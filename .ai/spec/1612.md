# Issue #1612 — tiered search cutover design checkpoint

## Requirement summary

The normal search authority will eventually move from the legacy event scan/index adapter to the tiered literal-search projection without allowing a parity run to compare the new implementation with itself. This foundation does **not** wire the cutover, execute DDL, drop legacy data, or add CLI/MCP maintenance commands. It establishes the explicit legacy rollback port and privacy-safe, store-bound parity-v2 evidence.

## Conceptual model and state machine

| Concept | State / behavior | Invariant |
|---|---|---|
| Search authority | `legacy` → `tiered` | One persisted authority controls normal reads; authority is projection-neutral and is not inferred from table presence, backfill progress, or process version. |
| Maintenance | `active`, `retiring`, `retired`, `restoring` | Retire and restore are explicit persisted transitions. A crash resumes the recorded transition; it never guesses from DDL. |
| Legacy adapter | `SearchLegacyPage` | Preserves pre-cutover membership and ordering and remains callable only by parity and rollback orchestration. |
| Parity evidence | v1 informational; v2 store-bound | v1 remains validator-readable but can never authorize `StartRetire`. v2 binds fixed evidence to the target store with its secret cursor key and covers both query classes criterion-by-criterion. |
| Projection | rebuildable optimization | Projection state is not the authority state. A missing/stale projection fails closed while tiered authority is active. |

Planned transitions:

| Current | Command | Preconditions | Persisted next state | Completion |
|---|---|---|---|---|
| `legacy/active` | `StartRetire` | valid v2 evidence bound to this store/revision; both evidence classes pass; projection complete | `legacy/retiring` | atomically switch authority to `tiered`, then mark `retired` |
| `tiered/retired` | `StartRestore` | legacy schema/data retained or restorable; compatibility check passes | `tiered/restoring` | restore legacy reader inputs, atomically switch authority to `legacy`, mark `active` |
| `*/retiring` | resume | transition record matches store | unchanged | idempotently continue or explicitly abort before authority switch |
| `*/restoring` | resume | transition record matches store | unchanged | idempotently continue; never drop the only readable representation |

## Responsibility assignment

| Responsibility | Owner | Not owner |
|---|---|---|
| Authority and maintenance transition invariants | future domain/application maintenance component | SQLite table-existence probes, CLI/MCP handlers |
| Persist/compare transition state and atomic authority switch | SQLite maintenance adapter | parity runner |
| Legacy membership/order implementation | `LegacyEventSearchQuery` SQLite adapter | normal tiered adapter |
| Tiered bounded coverage | `TieredEventSearchQuery` | legacy adapter |
| Evidence collection, privacy-safe binding, strict validation | `store-benchmark` parity runner | migration/DDL code |
| Protocol mapping | future CLI/MCP commands | domain transition rules |

## Boundaries / interfaces

- `LegacyEventSearchQuery.SearchLegacyPage(ctx, criteria)` is a consumer-oriented rollback/parity port. It always executes the legacy query and cannot silently select the tiered path.
- `TieredEventSearchQuery.SearchLiteralPage` remains the tiered evidence port.
- Normal `EventDatasource.Search` remains unchanged in this foundation. Future cutover code must dispatch from the persisted authority and must not reuse `SearchLegacyPage` as its normal implicit fallback.
- Parity v2 target binding is `HMAC-SHA256(cursor_key, canonical fixed aggregate/revision/store invariants)`. The artifact contains only the MAC, never the cursor key, database path, IDs, raw criteria, or an unkeyed hash susceptible to dictionary matching.
- Validator compatibility is explicit: v1 may be parsed for historical inspection; only a complete v2 suite can satisfy retirement authorization.

## Behavior tests and TDD plan

| Behavior / fault injection | Given | When | Then |
|---|---|---|---|
| Distinct dispatch | an adapter implementing both ports with call counters | legacy and tiered collectors run | legacy invokes only `SearchLegacyPage`; tiered invokes only `SearchLiteralPage` |
| Future cutover isolation | normal search changes later | parity runs | legacy side still calls the explicit legacy port, preventing self-comparison |
| Store binding | identical public aggregates in two stores with different cursor keys | binding is generated | bindings differ; artifact leaks neither key nor path/IDs/raw digest |
| Fixed evidence | revision/projection invariant changes | binding is recomputed | binding changes and stale evidence cannot authorize retire |
| Criterion scope | two required query classes | suite is validated | each criterion has its own binding/result; duplicated/missing classes fail closed |
| v1 compatibility | a valid historical v1 artifact | validate then authorize | validation succeeds; authorization is false |
| deadline/read error | either collector or invariant read fails | evidence finalizes | no equality proof or retirement authorization is emitted |
| transition crash (future) | crash before/after authority switch | resume | persisted state makes replay idempotent; fault-injection tests cover every write boundary |
| restore failure (future) | legacy restore is incomplete | restore runs | tiered authority remains until legacy verification completes |

TDD order: (1) red tests for explicit-port dispatch, then adapter extraction; (2) red tests for keyed store binding and v1/v2 authorization, then strict v2 schema/semantics; (3) future commits add transition aggregate and repository fault tests before wiring commands; (4) only after migration tests add non-dropping DDL and normal dispatch.

## Migration, compatibility, ordering, and rollback

- Initial migrations are additive and **must not drop** legacy FTS/search inputs. Retirement first means logical retirement; destructive cleanup requires a later release and separate compatibility evidence.
- Existing stores default to persisted `legacy/active`. Absence of a state row is interpreted only by a migration that writes that explicit default, not at query time.
- `SearchLegacyPage` preserves legacy descending-time ordering and offset semantics. Tiered cutover may change continuation mechanics, but the public result ordering contract must remain deterministic (`created_at DESC`, stable ID tie-break) and requires compatibility tests.
- Rollback trigger: any parity mismatch, incomplete coverage, store-binding mismatch, projection drift, elevated search errors, or ordering regression. Rollback uses persisted `StartRestore`; operators do not rename/drop tables manually.

## Split plan

1. **Foundation (this change):** design checkpoint, explicit legacy port/adapter, parity-v2 evidence primitives and tests. No cutover/DDL.
2. Add persisted maintenance/authority aggregate and SQLite repository with transaction/fault-injection tests; additive migration only.
3. Add retire/restore use cases and evidence authorization; keep normal search on legacy.
4. Wire normal CLI/MCP search to persisted authority, add compatibility/order and rollback integration tests.
5. After at least one compatibility window, propose legacy physical cleanup as a separate issue/PR with its own rollback plan.

## Self-review checkpoint

The foundation keeps decision rules out of handlers and SQL, makes the rollback implementation impossible to confuse with normal tiered search by interface name, and treats evidence as criterion-scoped authorization rather than a global “passed” boolean. The main residual uncertainty is the final public ordering contract across all query surfaces; therefore normal cutover is intentionally deferred.
