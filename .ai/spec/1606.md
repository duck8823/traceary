# v0.34.0 — Consolidate and reuse: the two pillars

Supersedes `docs/architecture/hot-cold-segmented-history.md` (+ `.ja.md`), which is removed by #1671.

## Structure-Behavior Design Note

### Requirement summary

**目的.** Traceary を二つの柱に絞り、その両方が確実に・自動的に働く状態にする。

1. **記録** — 取ることはできている。会話全体を持ち続けると肥大するので、**まとめ・圧縮・索引からの退避**を行う。
2. **記憶** — 上と重なる（まとめ・圧縮）が、加えて**そのまとめの自動利用**を行う。

この二つ目が「AI も睡眠をとった方がいい」の実装にあたる。生物の睡眠と同じく、**固定化は本人が意識してやらない**、**起床時には選別が終わっている**、**忘却は機能である**。

**現状（2026-08-07 実測、live store 24.71 GiB / 534,086 events / 26,728 sessions / 2.5 か月）.**

| | |
|---|---|
| 取る | 動いている。99.99% が hook 経由 |
| 肥大化 | +9.9 GiB/月。削減機構が 5 つあり全部オフ |
| 索引 | 15.83 GiB（全体の 64.1%）。全期間に trigram を張っている |
| 重複 | `events.body` 5.05 GiB のうち **2.91 GiB (57.7%) が完全重複** |
| まとめ | セッション要約が 26,728 中 **4 件** |
| 自動利用 | **配線ゼロ**。`additionalContext` / `hookSpecificOutput` はコードベースに 1 件も無い |

**期待する振る舞い.**

- 会話が溜まったら、**その場で**（素材がエージェントのコンテキストにあるうちに）まとまる
- 起床時には、**まとまったものだけ**が手元にある。生ログは渡さない
- 古い記録は索引から退避するが、**セッション単位では引ける**
- 本文を捨てても、**いつ・何を・何回**は永久に残る。**なぜ**はエージェントが実際に畳んだ範囲にだけ残り、機械的な gc 要約（`degraded=1`）に落ちた範囲では失われる

**非対象.**

- 外部ストレージへの分離（cold DB / segment file）。撤回済み
- 失敗捕捉（exit code）。ホスト側が payload に出さない
- コスト算出。`docs/research/ai-usage-source-verification.md` で明示的に見送り済み

### Conceptual model

| Concept | State | Behavior | Constraint / Invariant |
|---|---|---|---|
| **Event skeleton** | id, kind, session, workspace, agent, 時刻, `body_bytes`, `body_state` | 記録時に 1 度書かれる。**不変**: id / kind / session / workspace / agent / 時刻 / `body_bytes`。**可変**: `body_state` のみ（定義済み遷移に限る） | **永久**。行は削除されない。統計は不変フィールドだけから計算する |
| **Event body** | 本文。`event_bodies` に別置 | `body_state`: `present` → `discarded`（非 attested・畳み済み）／ `compressed`（attested） | attested な本文は削除されない。非 attested は畳まれるまで削除できない。`body_state` はこの遷移以外では動かない |
| **Attested record** | 人間の指示 (`prompt`) と実行したコマンドの同一性 (`command_text`, `input_text`) | 追記のみ | **永久**（圧縮のみ）。何を指示され、何を実行したかは消えない |
| **Command output** | 実行結果。`command_outputs` に別置 | 非 attested として扱う | 「何を実行したか」の証明に出力は要らない |
| **Refinement pressure** | セッションごとの未精製バイト数 | 各 stop で機械的に加算 | LLM を使わない。DB 更新 1 行 |
| **Session refinement** | セッション要約。世代・被覆範囲・生成者を持つ | 閾値超過時に**その場で**エージェントが書く。既存要約があれば**再まとめ** | **永久**。本文の約 1/500。これが残ることが本文を捨てられる条件 |
| **Recent index window** | 直近の生本文に張った trigram 索引 | 索引ファミリのバイト予算で押し出す | 予算は**索引ファミリ合計**で表現する（入力本文量ではない） |
| **Session tier index** | 全期間のセッション要約・キーワードに張った unicode61 索引 | 精製のたびに更新 | **永久**。「あのセッション」を特定できれば十分 |
| **Orphan range** | 畳まれないまま compact された範囲 | compact marker で記録 | 大きさは**典型的には**閾値未満（設計目標であり上限ではない）。gc で機械要約に落とす（参照時に畳まない）。入力が閾値を超えても扱えること |

### Responsibility assignment

| Responsibility | Owner | Reason to change | Not owner / reason |
|---|---|---|---|
| 何を記録するか | hook runtime | ホストの契約が変わったとき | 使用側は関与しない |
| いつ畳むべきか | stop hook の機械判断 | 閾値・圧力の定義が変わったとき | **LLM は判定に関与しない**（コスト） |
| 何を書くか（要約の中身） | エージェント（LLM） | — | Traceary は LLM を呼ばない（local-first） |
| 要約の保存と再まとめ | `session_refinements` + write port | 世代管理が変わったとき | hook は書式を知らない |
| 起床時に何を渡すか | 起床注入器 | 予算・選別規則が変わったとき | **選別は固定化時に済ませる**。起床時に判断しない |
| 索引に載せるか | search projection | 予算・トークナイザが変わったとき | 本文の生存とは独立 |
| 本文を捨てるか | `store gc` | 保持方針が変わったとき | 索引の退避とは独立の判断 |

### Boundaries / interfaces

| Boundary | Consumer | Hidden detail | Error contract |
|---|---|---|---|
| `stop` hook 終了コード | ホスト | 圧力計算・閾値 | 判定に失敗したら **exit 0**（作業を止めない） |
| 起床注入 (`additionalContext`) | ホスト | 要約の作り方・選別 | 要約が無ければ**何も出さない**（空文字を注入しない） |
| `traceary session refine` | エージェント | 世代・被覆範囲の管理。**テキストは合成しない**（渡された要約を保存し、generation / coverage だけを所有する） | 冪等。同じ範囲を二重に畳んでも要約は 1 つ |
| `event_bodies` / `command_outputs` | 読み取り経路 | 圧縮コーデック | 本文欠落は `body_state` で区別（エラーにしない） |
| 索引予算 | 運用者 | trigram 増幅率 | **索引ファミリ合計バイト**で指定する |

## ホスト契約（一次情報で確認、2026-08-07）

| ホスト | 起床時に注入 | stop で追加作業を依頼 | compact で依頼 | イベント占有 |
|---|---|---|---|---|
| Claude Code | ● `SessionStart` additionalContext | ● exit 2 →「continues the conversation」 | ✕ PreCompact は additionalContext 非対応 / PostCompact は「No decision control」 | 6.8% |
| Codex CLI | ● `SessionStart` stdout / additionalContext | ● `{"decision":"block","reason":...}` → continuation prompt | ✕ 注入不可 | 39.9% |
| Kimi Code | ✕ SessionStart は fire-and-forget → **初回 `UserPromptSubmit`** を使う | ● exit 2 →「a message can be appended to let the model continue」 | ✕「return values are completely ignored」 | 38.0% |
| Grok Build | ● SessionStart | ● Stop | ✕ | 2.4% |
| Antigravity | ● PreInvocation | ● Stop | **✕ compact hook 自体が無い** | 1.2% |
| Gemini CLI | ● SessionStart | ● AfterAgent | ✕ | ~0% |

**結論.**

- **compact はどのホストでも観測専用**。「compact 時に LLM を呼ぶ」は実装できない。梃子は **stop だけ**
- compact marker は「取り残し範囲」の記録にのみ使う
- Claude の PostCompact 本文（実測 186 件）は無料の素材として併用する
- ホスト差は **Kimi の起床注入だけ**（SessionStart → 初回 UserPromptSubmit）

## 睡眠サイクル

```
起きている間          hook が全部取る                          （動いている）
                          │
まとまってきたら      stop で機械判断（無料・毎ターン 2,811 回/日）
                      pressure >= 閾値 → exit 2 / decision:block
                      「今のセッションを畳んで書き込め」
                      ※ 素材はエージェントの頭の中にある。追加入力ゼロ
                      ※ 既存要約があるときは reason payload に
                        previous summary と covers_to を載せる
                          │
                      エージェントが（再）まとめを書き、
                      session_refinements へ refine で保存
                          │
寝ている間            store gc
                      索引から退避 / 非attested 本文を破棄 / attested を圧縮
                          │
起きるとき            SessionStart に完成済み要約だけを注入
                      ※ 生ログは絶対に渡さない
```

**再まとめの経路.** Traceary は LLM を呼ばない。再まとめのテキストはエージェントが書き、`traceary session refine` の write port は渡された内容を保存し generation / coverage だけを所有する（テキストは合成しない）。そのためエージェントが書く前に既存要約が手元に要る。既存要約と `covers_to` は、畳み依頼と同じ **stop hook の reason payload** で渡す。別の読み取りコマンドは足さない。

**閾値の意味.** 閾値は「LLM 呼び出し回数」ではなく、**取り残し範囲の設計目標** = 後から畳み直すときのコンテキスト汚染をどの程度に抑えたいか。**ハードな上限ではない**（典型的には閾値未満に収まるが、下の二経路では超えうる）。

この費用は**畳みを依頼する時点でエージェントの文脈が占められる量**であって、起床時の注入量ではない。起床時に入るのは完成した要約だけで、その量は閾値と無関係に自前の予算で決まる。

| 閾値 | 畳む時点の素材量 | 判断 |
|---|---|---|
| **64 KiB** | 約 16k トークン | **採用**（設計目標） |
| 256 KiB | 約 64k トークン | 畳みを頼む時点でエージェントの文脈を占めすぎる |
| 1 MiB | 約 250k トークン | 論外 |

呼び出し回数は、重複（96.6%）を潰した後のユニーク transcript が 2.5 か月で 145 MiB なので問題にならない。

**閾値を超えうる経路.**

1. **依頼の無視.** stop トリガーは繰り返し要求の抑止なしで出荷する（Risks / rollback 参照）。エージェントが畳まないまま圧力が閾値上に残り、応じる前に compact が来ると orphan range は閾値を超える
2. **単一 oversized turn.** 圧力は stop で評価するため、1 ターンで閾値を大きく超える記録（大きな tool output・長い transcript）が、評価点を挟まずに圧力を閾値下から大きく上へ押し上げる

これらから従う帰結:

- **gc の機械要約は入力が有界だと仮定してはならない** — 閾値を超える range も扱えること
- **起床時の注入予算は閾値から推論せず、独自に enforce すること**

## データ層

### テーブル

| テーブル | 持つもの | 寿命 | 索引 |
|---|---|---|---|
| `events` | skeleton のみ + `body_bytes` + `body_state` | **永久** | 現行 events 索引セット |
| `event_bodies` | `event_id`, `codec`, `payload` | 条件付き | PK のみ |
| `command_audits` | 実行の同一性: `command_text`, `input_text`, 結果コード | **永久** | `event_id` |
| `command_outputs` | `event_id`, `codec`, `payload` | 条件付き | PK のみ |
| `session_refinements` | `session_id`, `generation`, `covers_from`/`covers_to`, `summary`, `keywords`, `produced_by`, `produced_at`, `degraded` | **永久** | `session_id` |
| `session_orphan_ranges` | `session_id`, `from`/`to`, `observed_at` | 精製されるまで | `session_id` |
| `search_projection_recent_documents` + `_fts` | 直近窓の生本文 | **窓** | **trigram** |
| `search_projection_session_summaries` + `_keywords` | 全期間の要約 | **永久** | **unicode61 + porter** |
| ~~`event_metadata_projection`~~ | — | **廃止** | — |

### なぜ本文を別テーブルに出すのか

本文を `events` の列に持ったままだと、破棄が `UPDATE body=''` になる。SQLite はページを解放しないのでファイルは縮まず、縮めるには VACUUM（24 GB なら同容量の空きと数十分）が要る。別テーブルにして DELETE すればページが free list に入り、次の書き込みで再利用される。**VACUUM が不要になる**のが分ける理由。

副次的に、`events` が細くなると `event_metadata_projection` の存在理由が消える。あれは「本文を持つ太いテーブルを走査したくない」ための複製で、索引名まで一対一に対応している（実測）。

```
idx_events_workspace_session_created_at_norm_id_desc          0.10 GiB
idx_event_metadata_workspace_session_created_at_norm_id_desc  0.10 GiB   ← 同じもの
```

廃止で 0.47 GiB と索引の二重管理が消える。

### 索引を 2 層にする

| 層 | トークナイザ | 対象 | コスト |
|---|---|---|---|
| 直近（予算で縛る） | **trigram** | 生本文 | 本文の 2.16 倍（実測） |
| 全期間（永久） | **unicode61 + porter** | セッション要約・キーワード | 本文の約 1/500 |

現状は全期間に trigram を張っており、これが 15.83 GiB の正体。

**予算は索引ファミリ合計で表現する。** 現行の `recent_byte_limit` は `search_projection_recent_documents` の本文バイトを縛っており（`search_projection_rebuild.go:426`）、2 GiB 指定が 6.35 GiB の索引になる。運用者が見たいのは索引の総量なので、意味を合わせる。

### 一つの本文が辿る道

```
Day 0  ターン終了
  events        kind=transcript / 時刻 / bytes=42KB / state=present
  event_bodies  42KB の本文
  直近窓        trigram 索引に載る            → 「あの文字列」で全文検索できる

Day 0  stop hook が閾値超過を検出
  エージェントがその場で畳む → session_refinements
  この本文は「畳み済み範囲」に入る

Day 7  索引予算を超えて押し出される
  直近窓から退避                              → 全文検索では出ない
  セッション要約層では引ける                  → 「あのセッション」は見つかる
  events / event_bodies はそのまま            → 開けば中身は全部ある

Day 30 store gc
  event_bodies から DELETE
  ↓ 残るもの
  events               bytes=42KB, state=discarded   → 統計は永久
  session_refinements  何をしたか                    → 永久
  要約索引             あのセッションを引ける        → 永久
```

attested は別の道を通る。

```
prompt / command_text / input_text
  Day 7   索引からは退避する（検索の話）
  Day 30  gc で zstd 圧縮、state=compressed
  永久    削除されない（証跡の話）
```

### 三つの分離

同じ操作に混ざっている三つを、別々のイベントにする。

| 分離 | いつ | 失うもの | 残るもの |
|---|---|---|---|
| **索引から退避** | 窓の予算を超えたとき | 全文検索 | セッション単位の検索・本文・統計 |
| **本文を破棄** | 畳み済み かつ 非 attested | 中身 | バイト数・時刻・件数 |
| **圧縮** | attested | 何も | 全部 |

### 消えないもの / 消えるもの

| 何 | gc で消えるか |
|---|---|
| `events` skeleton（時刻・種類・バイト数・件数） | **消えない** |
| `session_refinements`（セッション要約） | **消えない** |
| セッション要約の索引 | **消えない** |
| `prompt` 本文（人間の指示） | **消えない**（圧縮のみ） |
| `command_text` / `input_text`（実行したコマンド） | **消えない**（圧縮のみ） |
| `transcript` 本文（エージェントの発言） | 畳んだ後に消える |
| `output_text`（コマンド出力） | 畳んだ後に消える |
| trigram 全文索引 | 窓から押し出されたら消える（本文は残る） |

**捨てるのはエージェントの喋りとコマンド出力だけ**で、「いつ・誰が・何を・何回」は残る。**なぜ**はエージェントが実際に畳んだ範囲にだけ残り、機械的な gc 要約（`degraded=1`）に落ちた範囲では失われる。

### 取り残し範囲

```
stop(畳む) ── やりとり ── stop(スルー) ── compact
             └────── 畳まれていない ──────┘
```

ここで失われるのはデータではない（hook は毎ターン記録済み）。失われるのは「安く畳める機会」だけ。orphan range の大きさは**典型的には**閾値未満だが、**定義上の上限ではない**（依頼の無視・単一 oversized turn — 閾値の意味を参照）。

扱い方は一つ。**gc で機械要約に落とす** — LLM 無しで「いつ・何を・何回・どのコマンド」は作れる。`degraded=1` を立てる。「なぜ」は失われる。入力が閾値を超えても機械要約はそれを前提に扱わねばならない。

**compact で所有が移る**（2026-08-08 決定）。畳みを依頼できるのは素材がエージェントの文脈にある間だけである。compact を通過した時点で未精製の範囲は文脈から外れるので、以後どれだけ stop を繰り返しても**その範囲はもう畳めない**。したがって compact 到達時に、未精製範囲は stop 圧力から切り離して orphan range として記録し、**圧力をリセットする**。以後の stop が見るのは compact 後の素材だけであり、切り離された範囲は gc の機械要約が引き取る。この境界を引かないと、二度と応じられない依頼を毎 stop 繰り返すことになる。

**「参照時に畳む」は撤回**（2026-08-08）。要約の執筆には LLM が要り、Traceary は LLM を呼ばない。畳みは呼び出し元が LLM だと分かっている経路からしか**依頼**できない。`traceary show` は人間が走らせうるので畳めない。残るのは consolidation トリガーが既に所有している stop hook だけである。参照経路を第二の依頼面にすると、第一経路が既に届く素材に対する面が増え、読み取り経路が書き込みになる。そして compact 後の範囲は参照経路から依頼しても畳めない（素材が文脈にない）ので、第二の面を足しても取り残しは減らない。

これで「畳んでいないから本文を捨てられない」詰まりも解消する。

### Risks / rollback

**手続き化リスク.** 「精製」を 1 つの巨大 usecase にしないこと。*圧力の判定* / *要約の保存* / *索引の退避* / *本文の破棄* は変更理由が違う。混ぜると gc がすべてを知る神クラスになる。

**premature abstraction リスク.** ホスト差は実測で **Kimi の注入先 1 点のみ**。ホストごとの Strategy を作らない。

**migration / compatibility.**

- 本文移送は 5 GiB の書き換えになる。**バッチ + チェックポイント**で行い、中断可能にする。`store payload-rehearsal` の既存機構を再利用する
- `event_metadata_projection` の廃止は読み取り経路の切り替えが先。同一 minor 内で二段階（並行運用 → 撤去）
- 索引の作り直しは既存の generation 機構に載せる（新規機構を作らない）
- 本番 DB での検証は禁止。`ref_live_db_migration_gap` のとおり、未リリース migration は巻き戻せない

**rollback trigger.**

- 本文移送後に `report` の統計が移送前と一致しない → 移送を中止し generation を破棄
- 起床注入で 1 セッションあたり注入量が予算を超える → 注入を無効化（記録は継続）
- stop hook の判定がターンを止める（exit 2 の暴発）→ 閾値を無限大にして無効化できること

**stop トリガーの runaway 抑止は載せない**（2026-08-08 決定）. stop トリガーは**繰り返し要求の抑止機構なし**で出荷する。エージェントが依頼を無視しても圧力は閾値上に残り、次の stop でもう一度依頼する。繰り返すのは compact までで、compact を跨いだ範囲は圧力ごと gc へ渡す（取り残し範囲を参照）。

根拠: 現状 Traceary の hook はどの経路も非ゼロ終了を返さない（すべて fail-open）。今回がユーザーのターンに干渉する初めてのケースで、ホスト側の continuation 挙動はここでまだ実測されていない。観測前に anti-runaway を積むのは、存在しないかもしれない失敗モード向けの実装になる。緩和は v0.34 タグ前の dogfood とし、ユーザー作業を中断するようなら閾値で無効化してパッチリリースする。依頼が無視されても失うものはない: 未畳み範囲は記録され、gc で機械的な `degraded=1` 要約に落ちる。
