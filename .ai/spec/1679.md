# v0.34.0-39 (#1679): express the search index budget in index bytes

Risk: **High** (schema migration, generation lifecycle, config semantics change).
Design consultation: gpt-5.6-sol, 2026-08-09. Implementation: Grok 4.5 high. Review: Claude Opus 5.

## Requirement summary

- Purpose: the operator-facing search budget must mean **physical bytes of the bounded
  search index family**, not bytes of the source text fed into it. Trigram measures
  2.16x the source, so today's knob understates the index by that factor.
- Current: `SearchProjectionBudget.RecentBytes` (default 64 MiB) is a ceiling on
  `SUM(search_projection_recent_documents.decoded_bytes)` — the indexed source text —
  applied only in the `eviction` phase (`search_projection_rebuild.go:441-451`).
- Expected: the knob is `IndexFamilyBytes`, default **1464 MiB (~1.43 GiB)**, derived
  from the #1620 store gate. The generation converts it to a source-text ceiling using
  a **measured** amplification ratio, persists the derivation, and reports the budget in
  the unit it is configured in.
- Non-goals: a unicode61+porter FTS table for the session tier; removing `--recent-age`;
  making the family stay under budget *while two generations coexist* (see "Not solved").

## What Sol established that changes the design

1. **"Stays under the configured budget across a rebuild" is not achievable** with the
   current lifecycle. `Start` leaves the previous generation in place
   (`search_projection_rebuild.go:71-100`), the `source` phase adds new-generation rows
   (`:610-638`), `eviction` only trims the new generation (`:441-451`), and the old one
   is removed in `cleanup` (`:455-457`). Peak is old-recent + old-non-recent +
   new-recent + new-non-recent. The honest guarantee is stated under "Guarantee".
2. **A previous generation's amplification cannot be the sole input to a hard cap.**
   Document-length distribution, trigram density, per-row fixed cost and FTS segment
   fragmentation all vary between generations. Two stages are required: a cheap estimate
   for the `source`-phase prefilter, then a measurement of *this* generation before the
   ceiling that actually governs eviction is fixed.
3. **`LIKE 'search_projection_recent%'` misclassifies.** `idx_search_projection_recent_eviction`
   and any `sqlite_autoindex_*` do not start with that prefix, and `_` is a LIKE wildcard.
   Classify on `name` **and** `tbl_name`, with `GLOB`.
4. **dbstat counts pages currently attributed to a b-tree.** Freelist pages are not
   counted, so a delete does reduce the figure — but FTS5 keeps deleted postings in a
   segment until merge, and the *file* does not shrink before `VACUUM`. Three different
   numbers must not be conflated: active b-tree allocation (dbstat), file size after
   `store compact`, and peak disk during a rebuild.
5. **Bumping `ConfigHash` to `v2:` alone strands every in-flight generation forever.**
   `Resume` rejects a hash mismatch (`search_projection_usecase.go:73-75`), `CatchUp`
   skips it (`:270-275`), and `StartGeneration` refuses while `rebuilding` (`:57-59`).
6. **A completed generation is never rebuilt on a config change.** `CatchUp` returns
   `already_complete` before reading `ConfigHash` (`search_projection_usecase.go:265-268`),
   so shipping a new default would be inert on every existing store.
7. **A full-corpus scan inside `Start` breaks the bounded store-open contract.** `Start`
   runs with no wall-time context (`search_projection_usecase.go:49-60`) on a path that
   promises one bounded unit of work per open (`search_projection_catchup.go:15-20`).

## Conceptual model

| Concept | State | Behavior | Constraint / Invariant |
|---|---|---|---|
| Index family budget | `search_projection_state.index_family_byte_limit` | operator input, one number | physical bytes of `search_projection_*` + `literal_search_*` |
| Capacity semantics version | `search_projection_state.capacity_semantics_version` | integer, currently 2 | a generation whose version is below the current constant is obsolete regardless of state |
| Amplification | `recent_amplification_ppm` | measured recent-family bytes per source byte, x1e6 | >= 1e6; falls back to 2 160 000 when unmeasurable |
| Non-recent reserve | `non_recent_family_bytes` | measured family bytes outside the recent tier | subtracted from the budget before conversion |
| Recent source ceiling | `recent_source_ceiling_bytes` | derived, persisted, re-derived once at source→eviction | the only number eviction compares against |
| Recent cutoff | `recent_cutoff_norm` | derived at Start, best effort | prefilter only; never a correctness input |
| Capacity evidence | `capacity_evidence_status` / `_reason` | `measured` / `unavailable` | a ceiling derived from a fallback is reported as estimated, never as verified |

## Responsibility assignment

| Responsibility | Owner | Reason to change | Not owner / reason |
|---|---|---|---|
| Measure family bytes split recent / non-recent | `infrastructure/sqlite` (dbstat) | SQLite physical layout | planner is pure and must stay so |
| Derive the source ceiling from the budget | `infrastructure/sqlite`, at Start and at source→eviction | conversion needs a measurement | planner has no access to physical bytes |
| Apply the ceiling | eviction SQL, from the persisted column | retention policy | not from `b.IndexFamilyBytes` directly — the caller's budget is not the derived ceiling |
| Decide `RetainRecent` | `application/usecase.PlanProjectionBatch` | pure policy over snapshot inputs | must receive the cutoff, not compute it |
| Decide a generation is obsolete | `application/usecase.CatchUp` | lifecycle policy | not the datasource |

## Design

### D1. Budget field and default

`SearchProjectionBudget.RecentBytes` → `IndexFamilyBytes int64`.
`Valid()` requires it > 0. `ConfigHash()` prefix `v1:` → `v2:`.

```go
// defaultSearchProjectionIndexFamilyBytes is the whole bounded search index
// family — documents, trigram index, session tier and literal fingerprints —
// measured as active b-tree allocation, not source text.
//
// 1464 MiB is what the 4 GiB store gate (#1620) leaves once every other Wave 3
// removal is applied; it is derived, not chosen.
//
// What it buys is a *variable* window, not a fixed one. Trigram measures 2.16x
// the source text, so this is roughly 0.66 GiB of indexable text. Measured
// weekly volume on the reference corpus varies eightfold (0.06 to 0.47 GiB per
// week), which is 1.5 to 2 weeks at the median rate, under a week during a
// heavy sprint and four to five weeks during a quiet one.
//
// Compression (#1685, #1742) buys losslessness, not reach: the index is built
// over plaintext, so a compressed body occupies exactly as much index as an
// uncompressed one. Everything older than the window stays reachable through
// the session tier, which is the design's answer to a short recent window.
const defaultSearchProjectionIndexFamilyBytes = 1464 << 20
```

The same text, condensed, is the `--index-family-bytes` flag usage string, and the CLI
default and `defaultSearchProjectionCatchUpBudget()` must both use the constant — they
already have to agree or `ConfigHash` blocks resume.

### D2. Family measurement, split

Replace `measureSearchProjectionFamilyBytes` (`search_projection_rebuild.go:873`) with a
version that returns `(recentBytes, nonRecentBytes int64, evidence CapacityEvidence)`.

Classification, per Sol finding 3:

```sql
SELECT COALESCE(SUM(CASE WHEN recent THEN pgsize ELSE 0 END),0),
       COALESCE(SUM(CASE WHEN recent THEN 0 ELSE pgsize END),0)
  FROM (SELECT d.pgsize AS pgsize,
               (s.name GLOB 'search_projection_recent*' OR s.tbl_name GLOB 'search_projection_recent*'
                OR s.name GLOB '*search_projection_recent*' AND s.type='index') AS recent
          FROM dbstat d JOIN sqlite_schema s ON s.name = d.name
         WHERE s.name GLOB 'search_projection_*' OR s.tbl_name GLOB 'search_projection_*'
            OR s.name GLOB 'literal_search_*'    OR s.tbl_name GLOB 'literal_search_*')
```

Settle the exact predicate against the real schema — the requirement is that
`idx_search_projection_recent_eviction`, the FTS5 shadow tables and any
`sqlite_autoindex_search_projection_recent_documents_*` all land on the recent side, and
that the total still equals what the current single-figure query returns. Prove both with
a test that asserts against `sqlite_schema` rather than a hand-written name list, so a
future table cannot silently escape the family.

The existing single-figure call sites (`cutover_family_bytes_before/after`) keep reporting
the total, i.e. `recent + nonRecent`.

### D3. Deriving the ceiling

```
amplificationPPM = recentBytes * 1e6 / sampleSourceBytes      (>= 1e6, else fallback)
sourceCeiling    = max(0, budget - nonRecentBytes) * 1e6 / amplificationPPM
```

`sampleSourceBytes` is `SUM(decoded_bytes)` over the rows the measurement saw. Require a
minimum sample (**8 MiB**) — below that the ratio is dominated by fixed per-table
overhead and is not a ratio of anything.

**Fallbacks, and why they are not fail-open.** Sol's position is that a hard cap must fail
closed when it cannot measure. Refusing to build a search index at all on a store without
`dbstat` is a worse outcome than building one against a documented estimate, so this
degrades instead — but it must never *claim* to be verified:

- no usable sample, or dbstat unavailable → `amplificationPPM = 2 160 000` (the #1620
  measurement) and `nonRecentBytes` = the last persisted measured value (0 on a fresh
  store, where it genuinely is 0). **No invented constants.**
- evidence is recorded as `unavailable` with the reason, and status reports the ceiling
  as estimated. `slog.Warn` once per generation.
- `nonRecentBytes >= budget` is **capacity exhausted**, not `sourceCeiling = 0`: fail the
  generation with a named class (`index_family_exhausted`) rather than silently building
  an empty recent tier.

**Two stages** (Sol finding 2):

- at `Start`, measure whatever is present (the previous generation) → this ceiling drives
  only the `source`-phase cutoff prefilter;
- at the **source→eviction transition**, measure again — the sample is now this
  generation's own rows — and re-derive `recent_source_ceiling_bytes`. Eviction compares
  against that column, never against `b.IndexFamilyBytes`.

### D4. The source-phase cutoff (prefilter, best effort)

Without it a rebuild inserts the whole `--recent-age` window into the trigram index and
immediately evicts most of it — on the reference corpus ~1.9 GiB of text built as ~4.1 GiB
of index to keep 0.66 GiB, and FTS5 does not fully return the deleted part before a merge.

At `Start`, under an explicit bounded context (Sol finding 7), find the timestamp at which
the corpus walked newest-first crosses `sourceCeiling`:

```sql
SELECT created_at_norm FROM (
  SELECT e.created_at_norm AS created_at_norm,
         SUM(CASE WHEN e.body_availability='available'
                  THEN COALESCE(e.body_plaintext_bytes,e.body_stored_bytes,length(CAST(e.body AS BLOB)),0)
                  ELSE 0 END
             + COALESCE(a.command_plaintext_bytes,length(CAST(a.command_text AS BLOB)),0)
             + COALESCE(a.input_plaintext_bytes,  length(CAST(a.input_text   AS BLOB)),0)
             + COALESCE(a.output_plaintext_bytes, length(CAST(a.output_text  AS BLOB)),0))
           OVER (ORDER BY e.created_at_norm DESC, e.id DESC) AS running
    FROM events e LEFT JOIN command_audits a ON a.event_id=e.id
   ORDER BY e.created_at_norm DESC, e.id DESC
) WHERE running > ? ORDER BY created_at_norm DESC LIMIT 1
```

The byte expression is the one `SelectSnapshot` already uses for `DecodedBytes`
(`search_projection_rebuild.go:375`) — reuse it, do not transcribe a second copy.
`length(CAST(x AS BLOB))` is deliberate: `length()` on TEXT counts characters, not bytes
(#1749).

- no row → the whole corpus fits; no byte cutoff.
- timeout or error → **no byte cutoff**, age-only, evidence `unavailable`. The eviction
  pass still enforces the ceiling, so this costs work, never correctness.
- retention is strict: keep `created_at_norm > cutoff`. Ties on an identical timestamp are
  dropped, which errs under budget.

`RetainRecent` becomes `created_at_norm > max(ageCutoff, byteCutoff)`, evaluated in the
pure planner from a new `ProjectionSnapshot.RecentCutoffNorm` — the planner must not learn
about dbstat.

**Where the estimate diverges from what is actually indexed, and in which direction:**

| divergence | direction | safe? |
|---|---|---|
| `body_text` joins four parts with `\n` (up to 3 extra bytes/row) | under-counts | negligible, and eviction corrects |
| events absent from `search_projection_source_sequence` / above `high_water` | over-counts | yes — window smaller than the budget allows |
| `body_availability != 'available'` contributes 0 to both | none | yes |
| legacy rows with NULL `*_plaintext_bytes` | would under-count without the CAST fallback → cutoff too old → **over budget** | handled by the CAST fallback; must be tested |

### D5. Making the change actually take effect (Sol findings 5 and 6)

Add `capacity_semantics_version INTEGER NOT NULL DEFAULT 1` and a constant
`searchProjectionCapacitySemanticsVersion = 2`. `Start` writes the constant.

`CatchUp`, **before** the `already_complete` return:

- persisted version < constant → the generation is obsolete under any state. Abandon it if
  one is in flight, then start a replacement. Log it at info with both versions.
- versions equal, `ConfigHash` differs → unchanged: an operator-owned rebuild with
  different tuning is skipped, not hijacked.

A version number rather than a hash of the value is deliberate: hashing the value would
make the auto path abandon an operator's deliberate `--index-family-bytes 500MiB`
generation.

### D6. Post-completion verification

`recordSearchProjectionCutoverEvidence` (`search_projection_rebuild.go:921`) already
measures the family after completion. It additionally records whether the measured total
is within `index_family_byte_limit`. Over budget → `slog.Warn` naming both figures, and a
status field. It does **not** loop evicting: FTS5 delete markers mean a loop is not
guaranteed to converge, and the recorded overshoot is the input that corrects the next
generation's amplification.

### D7. Status and reporting

`SearchProjectionStatus`: `recent_byte_limit` → `index_family_byte_limit`, plus
`recent_source_ceiling_bytes`, `recent_amplification_ppm`, `non_recent_family_bytes`,
`recent_cutoff_norm`, `capacity_evidence`, `index_family_within_budget`.
`recent_bytes` (source text actually retained) stays — it is now visibly the *other* unit,
which is the point.

## Guarantee (stated honestly, in the PR and in docs)

> After a generation completes and the previous generation has been reclaimed, the
> measured active b-tree allocation of the bounded search index family is at or below
> the configured budget. The figure is `dbstat` allocation, not file size: the file
> shrinks at `store compact`, and FTS5 returns space from deleted documents only as
> segments merge.
>
> **Not guaranteed during a rebuild.** `Start` keeps the previous generation readable
> until the new one is verified, so a rebuild transiently holds two families. The
> source-phase cutoff keeps the new one from being built at the full age window, but the
> transient peak is not bounded by this budget.

## Behavior tests

| Behavior | Given | When | Then | Level |
|---|---|---|---|---|
| Budget means index bytes | corpus whose trigram index is ~2x its text, budget B | generation completes | retained source ≈ B/amplification, not B | infra |
| Ceiling comes from the persisted column | ceiling persisted, caller passes a different budget | eviction batch | eviction honours the persisted ceiling | infra |

| Recent/non-recent split is exhaustive | live-shaped schema | measurement | recent+nonRecent equals the total family figure, and the recent side contains the index and FTS shadow tables | infra |

## Risks / rollback

- Renaming a column: migration 055 is new and unreleased in this branch. Editing it in
  place after any store has applied it silently skips the edit (#1685 lesson) — if it is
  edited during review, bump the digest and add the same defensive column check the
  payload backfill uses.
- `ConfigHash` v2 strands in-flight v1 generations. Mitigated by D5; without D5 this is a
  permanent skip, so D5 is not optional.
- Amplification feedback: a generation that over-measures ratchets the window down. Bounded
  by re-deriving from this generation's own sample at the eviction transition, and by
  clamping `amplificationPPM >= 1e6`.

## Follow-ups to file (do not implement here)

1. The two-generation rebuild peak is not bounded by the store gate — a lifecycle that
   reclaims before rebuilding, or an explicit rebuild capacity reserve.
2. `store compact` runs `VACUUM INTO` but never FTS5 `optimize`, so space from evicted
   documents is not returned until segments merge.
3. `ConfigHash` mixes capacity semantics with execution tuning (rows, wall time, lock
   time), so a performance-flag change blocks resume.
4. `--recent-age` is nearly always the looser bound once the byte budget is derived —
   is it a knob that does nothing?
5. Session tier tokenizer: the parent spec names unicode61+porter; the current exact
   keyword + `LIKE` satisfies #1679's acceptance. Measure quality and cost before adding
   an index inside the same budget.
