# #1676 — the gc state machine for eviction and discard

Issue: v0.34.0-36 "define the gc state machine for eviction, discard, and compression".
Parent: #1606. Branch: `feature/1676-gc-state-machine`.

## Structure-Behavior Design Note

### Requirement summary

- **目的**: gc が「何を失い、何を必ず残すか」を軸ごとに分離して定義し、コードで強制する。
- **現状**: `traceary store gc --target events` は
  `DELETE FROM events WHERE created_at < ?`（`infrastructure/sqlite/sql/delete_old_events.sql:1`）で
  行ごと削除し、`command_audits` は FK で cascade する
  (`schema/sqlite/migrations/000003_create_command_audits.sql:1-7`)。
  結果として #1676 が「never removed by gc」と宣言した 4 項目
  （events skeleton / `prompt` 本文 / `command_text` / `input_text`）が**すべて消えている**。
- **期待する振る舞い**: gc は行を削除せず、資格のある本文だけを破棄する。
- **非対象**: 圧縮（v0.35 / #1693）、attestation（v0.34 に概念が存在しない）、
  `command_outputs`（#1675 が圧縮で解決済み。後述 D5）。

### Measurements (live store, 2026-08-10, schema 34, 29.4 GB, `PRAGMA query_only`)

| kind | rows | body bytes |
|---|---|---|
| transcript | 242,187 | 3.146 GiB |
| command_executed | 280,437 | 1.918 GiB |
| prompt | 35,976 | 0.743 GiB |

591,113 events すべてが `body_availability='available'`。
raw-body retention は**一度も実行されていない**。

v0.34 出荷時点では同じコーパスが既に別の merge 済み作業で縮む。
migration 048 が `command_audits` peer を持つ `command_executed` の `events.body` を消し、
#1682 が transcript を dedupe し、#1685 が zstd を backfill する（transcript 2.44x）。
#1685 の実測で post-dedupe / post-zstd の transcript は **0.143 GiB**。

**したがって #1676 は容量施策ではない。** 破棄で回収できるのは最大 0.1 GiB 程度であり、
#1620 の 4 GiB ゲートは圧縮で閉じていて gc に依存していない。
#1676 の価値は**安全契約**にある。

## Decisions

### D1 — `body_state` 列は追加しない

`rg -n 'body_state|BodyState'` はリポジトリ全体で 0 件。
Issue は「Depends on #1685 (`body_state` must exist)」と書くが、#1685 は途中で
「payload codec を既存コーパスへ適用する」へ rescope され、`body_state` を導入していない。
依存は未達であり、この issue で導入するか不要と示すかの二択になる。

破棄の軸は既に存在する。
`schema/sqlite/migrations/000026_add_raw_body_retention.sql:1-2`

```sql
body_availability TEXT NOT NULL DEFAULT 'available'
    CHECK (body_availability IN ('available', 'unavailable_retention'))
```

`body_state` を足すと同じ事実の二重表現になり、二者が矛盾しうる。追加しない。

**gpt-5.6-sol の指摘を受けた訂正**: 当初案は「圧縮軸は `body_codec` なので v0.35 の第三状態は
そこに入る」としていたが、これは誤り。`body_codec` は *representation* metadata であって
body lifecycle state ではなく、しかも decoder は `identity` / `zstd` 以外を拒否する
(`infrastructure/sqlite/payload_codec.go:124-143`)。`body_codec='future'` は schema が受理しても
`show` が integrity error で落ちる。第三の *codec* が additive なのは schema だけで、動作は additive ではない。

正しい根拠はこうである。
`body_availability` は CHECK 付き閉集合なので、**新しい値**を足すには `events` の
テーブル再構築（12-step ALTER）が要る。583k 行の `events` に対する再構築は、
additive のみを許す rollback 契約
(`schema/sqlite/migrations/000055_add_search_projection_index_family_budget.sql:8-12`) と衝突する。
よって将来の破棄理由（redaction、法的削除、sensitive-path 分類など。
分類自体は `application/sensitivepath/classify.go` に既にあり redaction とは別物）は
**`body_availability` の新しい値ではなく、後から additive に足す reason sidecar 列**として表現する。

これで DoD「third value needs no data migration」は満たされる。
今この列を作らないのは、v0.34 に理由が 1 つしか存在しないためである
（実在しない variation のために抽象を作らない）。拡張点は本 spec と `docs/storage/README.md` に明記する。

### D2 — `gc --target events` は行削除をやめ、本文破棄に変わる（本 issue の主眼）

利用者判断（2026-08-10, AskUserQuestion）: **「行削除をやめ本文破棄に変える」**。

`collectGarbageInTx` の events 分岐
(`infrastructure/sqlite/store_management_datasource.go:478-486`) の
`deleteOldEventsQuery` を破棄 UPDATE に置き換える。events 行は gc では二度と消えない。

帰結として `--target sessions` の `delete_empty_sessions.sql:4-8`
（`NOT EXISTS (SELECT 1 FROM events WHERE events.session_id = sessions.session_id)`）は
事実上 event 削除に養われなくなる。session 行は skeleton 相当の小さなメタデータであり、
「events skeleton は消さない」と整合する。**この縮退はドキュメントに明記**し、
`--target sessions` は表面削減の候補として follow-up 起票する（/goal 項目 4）。

### D3 — 破棄の述語は positive allowlist

資格は次の**すべて**を満たす行に限る。

1. `kind = 'transcript'` — allowlist。`prompt` も将来の新 kind も既定で安全側。
2. `body_availability = 'available'`
3. `ts_norm(created_at) < ts_norm(cutoff)`
4. **session が存在し** `ended_at IS NOT NULL`
5. `session_refinements` の被覆範囲内

4 は gpt-5.6-sol の MUST を採用した変更である。現行は
`NOT EXISTS(active session)`（`raw_body_retention_datasource.go:57-60`）で、
session 行が**無い**イベントを「終了済み」と見なす。`events` には session への FK が無い
(`000001_init.sql:1-8`) ので、これは実際に起こりうる。証拠の不在を証拠として扱わない。

5 の順序は既存の refinement upsert と同じ `(ts_norm(created_at), id)` 辞書順
(`infrastructure/sqlite/sql/upsert_session_refinement.sql:38-49`) に揃える。
`covers_from_event_id` / `covers_to_event_id` は nullable なので両方 NOT NULL を要求する。
`e.session_id` が NULL なら被覆不能 = 非候補（安全側）。

### D4 — degraded な機械 fold も fold として認める

利用者判断（2026-08-10, AskUserQuestion）: **「gc の機械 fold を fold として認め破棄可」**。

gpt-5.6-sol は「gc は削除直前に自分で `degraded=1` の機械要約を書く
(`docs/storage/README.md:170-175`) ので、fold ゲートが自己満足になる」として
degraded を不可とすべきと主張した。**採用しない。**

理由は #1676 自身の契約にある。破棄で失われると宣言されているのは "the text" だけで、
残すと約束したのは "bytes, timestamps, counts" である。gc の orphan consolidation が書く
機械要約は「いつ・どの event kind が・何回・どのコマンドが走ったか」を保持しており、
まさにその約束を満たす。agent の推論を失うことは #1676 の破棄行の定義どおりである。

代わりに、gate が空虚にならないよう **fold の存在自体は述語として強制する**。
orphan consolidation が失敗した target では従来どおり run を中断する
(`presentation/cli/gc.go:83-93`)。fold が書けなければ破棄も起きない。

### D5 — 統計は現状で正しい。production 変更ではなくテストで固定する

当初案「破棄時に上書きされる論理バイト数を保存する」は誤りだった。gpt-5.6-sol の指摘で 2 点訂正する。

- `body_stored_bytes` は**上書きされていない**。`raw_body_retention_datasource.go:249-257` は
  設定せず、026/053 の trigger は `WHEN NEW.body_availability = 'available'` なので発火しない
  (`000053_codec_aware_body_derivations.sql:15-28`)。pre-codec provenance として意図的に保存されている。
  ここを marker サイズに変えると、resumable apply の検証
  (`raw_body_retention_datasource.go:307-320`) が元の候補 extent を期待しているため壊れる。
- `body_plaintext_bytes` は**統計ではなく復号の整合性チェック**である
  (`infrastructure/sqlite/payload_codec.go:75-98,124-159`)。本文を marker に置き換えつつ元の長さを
  残すと codec tuple が矛盾し、`loadEventPlaintext` が integrity error で落ちる。
  さらに availability を見ずに `body_plaintext_bytes` を予算計算に使う経路がある
  (`event_search_authority.go:157-178`、`literal_search_query.go:88-115`、
  `sql/select_session_body_bytes.sql`、`sql/select_session_body_bytes_after.sql`) ので、
  歴史的な値を残すとこれらが嘘をつく。

よって `body_original_bytes` と `body_stored_bytes` が不変であること、
codec tuple が marker を正しく記述していること、行数・timestamps・kind が不変であることを
**テストで固定する**。production の変更は無い。

### D6 — gc の破棄は ledger を書かない

`store retention` は plan / review / recovery archive を伴う復元可能な経路であり、
`raw_body_retention_entries` はその成果物である。gc には plan が無い。

gc の破棄は `body_availability`、`body_pruned_at` を直接更新し、
`body_pruned_plan_id` は **NULL のまま**にする。これが 2 経路の provenance を区別し、
将来の reason sidecar (D1) の種になる。gc 破棄は復元不能であり、これは gc の従来の意味と同じ。
`store retention` は review 可能で recovery archive から復元できる経路として残る。

marker は既存の `domtypes.EventBodyUnavailableRetentionMarker` を
`encodePayload(..., payloadCodecIdentity)` で符号化したものを再利用する。
zstd → identity の遷移は counter guard
(`000036_add_payload_codec_foundation.sql:49-51`) を通る（underflow check であって禁止ではない）。
既存の retention apply が同じ遷移を実行済みなので経路は実証されている。

### D7 — plan/apply の TOCTOU を塞ぐ（`store retention` 側）

gpt-5.6-sol の MUST を採用。`ListRawBodyCandidates` に資格を足すだけでは足りない。
apply は body identity と active session しか再検査せず、kind・session 終了・被覆を見ない
(`raw_body_retention_datasource.go:302-341`)。
plan 後に refinement を消してから apply すると、被覆されていない本文が破棄される。

`verifyRawBodyCandidateState` と同じ transaction で **D3 の述語全体**を再検査する。

### D8 — `command_outputs` は対象外

#1675 は command output の容量を圧縮 2.57x と migration 048 の重複除去で解決し、
cap を明示的に却下し、「v0.34 に attestation は無い」と明記して終わっている。
#1676 の "Removed once folded: `command_outputs`" は自らの依存先の結論に上書きされている。

## Conceptual model

| Concept | State | Behavior | Constraint / Invariant |
|---|---|---|---|
| Event body | `available` / `unavailable_retention` | discard | `prompt` は永久に `available`。skeleton は不滅 |
| Body representation | `body_codec` = `identity` / `zstd` | encode / decode | availability とは直交。破棄後は必ず `identity` + marker |
| Index membership | recent tier に居る / 居ない | evict | events を一切変更しない（#1679 で分離済み） |
| Fold | `session_refinements` 行の被覆範囲 | 単調に前進 | 被覆は破棄の前提。degraded も可（D4） |

```
body:   available --(folded ∧ ended ∧ transcript ∧ old)--> unavailable_retention
index:  present   --(over index-family budget)-----------> absent   (body untouched)
```

| Responsibility | Owner | Reason to change | Not owner / reason |

## Boundaries / interfaces

| Boundary | Consumer | Hidden detail | Error contract |
|---|---|---|---|
| `CollectGarbage(ctx, before, target, dryRun) (int, error)` | CLI | 削除か破棄か | 既存どおり。返り値の意味が「削除行数」から「破棄本文数」に変わる |
| `store gc` 出力 / JSON | 人・スクリプト | — | 語彙を deleted → discarded に更新。events target のみ |
| `store retention plan/apply` | 運用者 | 資格述語 | plan が stale なら apply は失敗する（D7） |

新しいコマンド・サブコマンド・フラグ・MCP tool は**足さない**。

## Risks / rollback

- **手続き化リスク**: 資格述語を SQL と Go の両方に書くと必ず乖離する。単一の `.sql` を
  gc と retention の双方から `go:embed` で共有する。
- **migration**: schema 変更は無い。列も trigger も足さない。rollback 契約に影響しない。
- **回収量の激減**: `gc --keep-days 90 --target events` が返す件数の意味が変わり、
  実バイト回収は大幅に減る。ライブ store は gc 未実行・591k 件全件健在なので既存データへの影響は無い。
  ゲート #1620 は圧縮で閉じており gc に依存しない。
- **`--target sessions` の縮退**: D2 の帰結。ドキュメント化し follow-up で表面削減を検討。
- **rollback trigger**: `gc --target events` の破棄が意図しない kind に及んだ場合。
  復元は不可能なので、resume 可能な batch ではなく allowlist の厳格さで担保する。

## Follow-ups (v0.34 フォローアップとして起票する)

1. `SaveIfAdvances` は `covers_from_event_id` を上書きするが SQL guard は `covers_to` しか見ない
   (`sql/upsert_session_refinement.sql:29-49`)。generation 2 で `[e2,e3]` を `[e1,e2]` に上書きすると
   e1 が unfold される。下限の非後退も要求すべき。
2. retention plan の回収見積もりが過大。選択された encoded サイズではなく decode 済み
   plaintext 長を合算している (`raw_body_retention_datasource.go:52-92`、
   `raw_body_retention_usecase.go:53-65,90-93`)。
3. `body_codec` に CHECK が無く、未対応値は書けてしまい read 時にだけ失敗する
   (`payload_codec.go:124-143`)。
4. `gc --target sessions` は D2 後に event 削除から養われなくなる。表面削減の候補（/goal 項目 4）。
