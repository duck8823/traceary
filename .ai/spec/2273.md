## 1. Requirement summary

### 1.1 Problem (restated from the issue, verified)

`requestConsolidationIfDue` (`presentation/cli/hook_consolidation.go:87-139`) measures unrefined body-byte pressure after a durable transcript write and, when `result.Due`, returns `consolidationExitError` — exit 2 plus a stderr reason. Verified: the function's only non-exit output is `slog.Debug` (lines 104, 110, 114, 120, 128), all behind the debug logger. **Nothing is persisted.** So "how many times was an agent asked to refine, and how often did it comply" is unanswerable today; the #2272 spike had to infer it from Stop counts.

### 1.2 Acceptance criteria (verbatim scope — do not shrink or widen)

- **AC1** Every emitted consolidation request records a metadata-only fact: session id, client, pressure value, threshold, whether it was a re-request for the same session, and the delivery path (`stop exit-2` / `additionalContext` / `none`). It must survive spool replay semantics without double counting.
- **AC2** `traceary session refine` records its outcome against the most recent request for that session (accepted / rejected + reason), so requests and refinements join.
- **AC3** `doctor` shows, per host, over the last 7 days: requests, sessions requested, refinements written (by `produced_by`), and the conversion ratio; O(1)/bounded like the other doctor signals.
- **AC4** The v0.48 release gate in #2263 reads this doctor output during pre-release dogfood. *(No code in this PR — see §7.4.)*
- **AC5** Tests: request → refine → doctor ratio; re-request counted once per cadence; spool replay does not emit a request.
- **Constraint** No schema change beyond an additive event kind or ledger table.

### 1.3 Non-goals (out of scope, do not implement here)

Changing the trigger signal (#2274); the `stop_hook_active` guard and reason text (#2275); any new `EventKind`; bundle export/import of the ledger; per-workspace breakdown; a config knob for the doctor thresholds; MCP or `--json` surface on any existing command.

## 2. Conceptual model

Three concepts, one new aggregate.

**Consolidation request** — a *fact about Traceary's own behaviour*: at instant T, for session S on host C, pressure P crossed threshold H and we asked the agent to fold, delivered over path D. It is bookkeeping, not session content. It is immutable once written except for the single outcome amendment below.

**Refine outcome** — the amendment: the most recent still-open request for S is later stamped with what the agent actually did (`accepted` / `rejected`), a short reason token, the `produced_by` of the refinement, its generation, and when.

**Conversion** — the derived read: over a window, per host, `sessions_refined / sessions_requested`.

### 2.1 Decision: SQLite ledger table, not a new event kind — CONFIRMED

Fable 5 chose a `consolidation_requests` table over an additive `EventKind`. **Confirmed.** Verified reasons:

1. A new kind must be appended to `knownEventKinds` (`domain/types/event_kind.go`), which changes `KnownEventKindStrings()` and therefore `--kind` validation/help, `list`/`search`/`context` output and the frozen JSON contract goldens in `presentation/cli/golden_test.go`.
2. The event table is the thing the trigger measures. A request row in `events` would appear in the "latest event to cover" reasoning the refine skill tells the agent to use for `covers_to`, and in every "events since X" signal #2274 introduces. A measurement instrument must not perturb what it measures.
3. A hook-state file cannot be joined to `session_refinements` in SQL, and AC3's ratio is a join.

### 2.2 Decision: idempotency key — CONFIRMED with a correction

Fable 5 used `UNIQUE (session_id, at_event_id)`. **Confirmed**, and it is belt-and-braces rather than the sole guard — see §6.2 for the upstream guard that already prevents the common double-count. Keep it: it is cheap, it is self-explanatory, and `at_event_id` is independently useful (it is the boundary the pressure was measured at, so a later refinement's `covers_to` can be compared against it).

**Correction:** Fable 5 planned to obtain the boundary by adding `LatestEventIDAfter` to `SessionConsolidationPressureRepository`. That repository's doc comment scopes it to "measures unrefined body-byte pressure … no writes"; a latest-id lookup belongs to `SessionEventOrderRepository` (`domain/model/session_event_order_repository.go:13-17`), which already owns `EarliestEventID`, `FindEventSessionID`, `EventIsStrictlyAfter` and is documented as "the canonical-order questions … about events". Put `LatestEventID` there. See §8-D2 and §4.3.

```sql
-- 000075_create_consolidation_requests.sql
--
-- consolidation_requests is the measurement ledger for the stop-hook fold
-- request (#1674, #2273). One row per emitted request. It is bookkeeping about
-- Traceary's own behaviour, not session content, which is why it is a table and
-- not an events row: an events row would appear in the "latest event to cover"
-- reasoning the refine skill hands the agent, perturbing the very signal the
-- trigger measures.
--
-- requested_at is stored in the FIXED-WIDTH canonical form that ts_norm emits
-- (see formatMemoryValidityTimestamp / normalizeRFC3339NanoForCompare), NOT the
-- variable-width RFC3339Nano that formatTimestamp emits. Variable-width is not
-- lexically ordered ('.' 0x2E < 'Z' 0x5A), so a plain TEXT range scan over it is
-- wrong near a fractional-second boundary (#1185). Storing the canonical form
-- makes the 7-day window scan boundary-correct AND index-usable, and makes
-- `ts_norm(session_refinements.produced_at) >= requested_at` a valid comparison
-- without normalising both sides at read time.
CREATE TABLE consolidation_requests (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id            TEXT    NOT NULL,
    client                TEXT    NOT NULL,
    requested_at          TEXT    NOT NULL,
    -- Latest event of the session when we asked: the boundary the pressure was
    -- measured against, and the idempotency key together with session_id.
    at_event_id           TEXT    NOT NULL,
    -- 'body_bytes' today; #2274 may introduce another signal without a migration.
    signal                TEXT    NOT NULL,
    pressure_value        INTEGER NOT NULL,
    threshold_value       INTEGER NOT NULL,
    re_request            INTEGER NOT NULL CHECK (re_request IN (0, 1)),
    delivery              TEXT    NOT NULL CHECK (delivery IN ('stop_exit_2', 'additional_context', 'none')),
    -- NULL until traceary session refine stamps the outcome. NULL means "asked,
    -- still open"; it is the definition of an open request.
    refine_outcome        TEXT    CHECK (refine_outcome IN ('accepted', 'rejected')),
    -- A fixed token (created / superseded / unchanged / invalid_covers_to /
    -- usecase_error). NEVER err.Error() and never summary text: this table is
    -- metadata-only and must not echo session content.
    refine_reason         TEXT    NOT NULL DEFAULT '',
    refine_produced_by    TEXT    NOT NULL DEFAULT '',
    refined_at            TEXT,
    refinement_generation INTEGER,
    UNIQUE (session_id, at_event_id)
);

-- FindLatestOpen: newest row for a session.
CREATE INDEX idx_consolidation_requests_session_id_desc
    ON consolidation_requests(session_id, id DESC);
-- Doctor's 7-day window scan. requested_at leads so the range is a seek, not a
-- table scan; client follows so the GROUP BY is satisfied from the index.
CREATE INDEX idx_consolidation_requests_requested_at_client
    ON consolidation_requests(requested_at, client);
```

`re_request = 1` when a row already exists for the same `session_id` with `refine_outcome IS NULL` — i.e. we asked again before any refinement landed. `delivery` is `stop_exit_2` for all three allowlisted hosts today (`hook_consolidation.go:29-33`); the other two values are reserved so #2274/#2275 can record honestly without a migration.

```go
// recordConsolidationRequest writes the metadata-only measurement fact for a
// request that is about to be delivered. It returns nothing: no outcome here may
// alter the caller's exit status (#2273).
func (c *RootCLI) recordConsolidationRequest(
	ctx context.Context,
	sessionID types.SessionID,
	client string,
	result usecase.ConsolidationPressureResult,
	threshold int64,
) {
	if c.consolidationRequest == nil || c.sessionEventOrder == nil {
		return
	}
	latest, err := c.sessionEventOrder.LatestEventID(ctx, sessionID)
	if err != nil {
		slog.Debug("consolidation request not recorded: latest event lookup failed",
			"session_id", sessionID.String(), "error", err)
		return
	}
	atEventID, ok := latest.Value()
	if !ok {
		slog.Debug("consolidation request not recorded: session has no events",
			"session_id", sessionID.String())
		return
	}
	recorded, err := c.consolidationRequest.Record(ctx, usecase.ConsolidationRequestInput{
		SessionID:      sessionID,
		Client:         client,
		AtEventID:      atEventID,
		Signal:         consolidationSignalBodyBytes, // const "body_bytes"; #2274 may add another
		PressureValue:  result.PressureBytes,
		ThresholdValue: threshold,
		Delivery:       types.ConsolidationDeliveryStopExit2,
	})
	if err != nil {
		slog.Debug("consolidation request not recorded", "session_id", sessionID.String(), "error", err)
		return
	}
	slog.Debug("consolidation request recorded",
		"session_id", sessionID.String(), "recorded", recorded.Recorded, "re_request", recorded.ReRequest)
}
```

`c.sessionEventOrder` is a new optional `RootCLI` field holding `model.SessionEventOrderRepository`; wire `eventDatasource` into it from `main.go`. (`RootCLI` already holds repository-shaped ports elsewhere, e.g. `sessionWakeSummary`.)

Delivery is `stop_exit_2` unconditionally: `requestConsolidationIfDue` returns early for any client not in `consolidationStopClients` (`:29-33, :94-96`), and all three of `claude`/`codex`/`kimi` deliver via exit 2.

**Q1 — `sql/select_consolidation_conversion.sql`** (bind: `since`)

```sql
-- Bounded by idx_consolidation_requests_requested_at_client. requested_at is
-- stored in ts_norm canonical fixed-width form, so this plain TEXT range scan is
-- boundary-correct (#1185) and index-usable; do not wrap either side in ts_norm.
SELECT client,
       COUNT(*)                                                                  AS requests,
       COUNT(DISTINCT session_id)                                                AS sessions_requested,
       SUM(CASE WHEN refine_outcome = 'accepted' THEN 1 ELSE 0 END)              AS requests_accepted,
       COUNT(DISTINCT CASE WHEN refine_outcome = 'accepted' THEN session_id END) AS sessions_refined
  FROM consolidation_requests
 WHERE requested_at >= ?
 GROUP BY client
 ORDER BY client
```

**Q2 — `sql/select_consolidation_refinement_authorship.sql`** (bind: `since`)

```sql
-- "refinements written, by produced_by" (AC3), restricted to sessions we asked
-- in the window and to refinements that landed at or after the first ask for
-- that session. Bounded by the number of DISTINCT sessions asked in 7 days; each
-- join leg is a session_refinements PRIMARY KEY point lookup, so this never
-- scans that table.
--
-- ts_norm is applied to session_refinements.produced_at because that column is
-- written by formatTimestamp (variable-width RFC3339Nano) and is therefore not
-- lexically ordered (#1185). Wrapping it here costs nothing: it is evaluated on
-- the handful of already-located rows, not used to drive an index. ts_valid
-- fails an undatable produced_at closed — it lands in the '' (none) bucket
-- rather than being credited as compliance.
SELECT r.client,
       COALESCE(sr.produced_by, '') AS produced_by,
       COUNT(*)                     AS sessions
  FROM (SELECT client, session_id, MIN(requested_at) AS first_requested_at
          FROM consolidation_requests
         WHERE requested_at >= ?
         GROUP BY client, session_id) AS r
  LEFT JOIN session_refinements AS sr
         ON sr.session_id = r.session_id
        AND ts_valid(sr.produced_at) = 1
        AND ts_norm(sr.produced_at) >= r.first_requested_at
 GROUP BY r.client, produced_by
 ORDER BY r.client, produced_by
```

`since` is bound as the fixed-width canonical string (`formatMemoryValidityTimestamp(now.UTC().Add(-consolidationConversionWindow))`), matching how `requested_at` is stored. **Never** bind `formatTimestamp(...)` here.

This Q2 shape is a deviation from Fable 5's `SELECT produced_by, COUNT(*) FROM session_refinements WHERE produced_at >= ? GROUP BY produced_by` — see §8-D3.

### 5.3 Outcome path — `session_refine.go`

`runSessionRefine` (`presentation/cli/session_refine.go:70-113`) has six error exits. Only those *after* `types.SessionIDFrom` succeeds can be attributed to a session, so only those are recordable:

| Exit | Recordable? | Outcome | `refine_reason` |
|---|---|---|---|
| `storeManagement` / `sessionRefinement` nil, `resolveDBPath`, `Initialize` fail | no — no session id parsed yet, or no store | — | — |
| `types.SessionIDFrom` fails | no — there is no session to attribute to | — | — |
| `types.EventIDFrom(covers-to)` fails | yes | `rejected` | `invalid_covers_to` |
| `Refine` returns an error | yes | `rejected` | `usecase_error` |
| `Refine` → `created` | yes | `accepted` | `created` |
| `Refine` → `superseded` | yes | `accepted` | `superseded` |
| `Refine` → `unchanged` | yes | `rejected` | `unchanged` |

**`unchanged` maps to `rejected`, not `accepted`** — a deviation from Fable 5, see §8-D4. Rationale: `SessionRefineOutcomeUnchanged` means "the incoming covers_to did not advance coverage, so generation and text were left alone" (`domain/model/session_refinement.go:169-171`). Coverage did not move, so pressure does not fall, so the next Stop asks again. Counting a replay as compliance would make the conversion ratio report success on exactly the sessions that keep re-firing — the failure mode #2272 measured. The reason token `unchanged` keeps the distinction from a genuine rejection visible in the ledger.

`refine_reason` is **always** one of these seven fixed tokens. Never `err.Error()`: a wrapped usecase error can contain the summary or the covers-to string, and this table is metadata-only (#2263 owner policy: audit records the fact, not the content).

```go
	coversTo, err := types.EventIDFrom(input.coversTo)
	if err != nil {
		c.stampConsolidationRefineOutcome(cmd.Context(), sessionID,
			types.ConsolidationRefineRejected, consolidationReasonInvalidCoversTo, producedBy, types.None[int]())
		return xerrors.Errorf("%s: %w", Localize("invalid covers-to event id", "covers-to イベント ID が不正です"), err)
	}
```

Note `producedBy` defaulting (`session_refine.go:94-97`) currently happens *after* the `covers-to` parse; move the three-line default block above it so the rejected stamp carries the right value. That is a pure reordering with no behavioural effect on the success path.

```go
	result, err := c.sessionRefinement.Refine(cmd.Context(), usecase.SessionRefineInput{...})
	if err != nil {
		c.stampConsolidationRefineOutcome(cmd.Context(), sessionID,
			types.ConsolidationRefineRejected, consolidationReasonUsecaseError, producedBy, types.None[int]())
		return xerrors.Errorf("%s: %w", Localize("failed to refine session", "session の refine に失敗しました"), err)
	}
	c.stampConsolidationRefineOutcome(cmd.Context(), sessionID,
		consolidationOutcomeFor(result.Outcome()), string(result.Outcome()),
		producedBy, types.Some(result.Refinement().Generation()))

	return printSessionRefineResult(output, result, input.asJSON)
```

`stampConsolidationRefineOutcome` returns nothing, nil-checks `c.consolidationRequest`, and `slog.Debug`s any error. **The command's exit status, stdout and `--json` contract are unchanged in every branch** — the join is a side effect.

`MarkRefineOutcome` targeting "the newest row with `refine_outcome IS NULL`" satisfies AC2's "most recent request": if the newest request is already stamped, a second refine for the same session finds no open row and is a silent no-op, which is correct — there was no outstanding ask to answer.

## 10. Risks / rollback

| Risk | Severity | Mitigation |
|---|---|---|
| Ledger write breaks the Stop hook | **High if wrong** | `recordConsolidationRequest` returns nothing and cannot alter the exit path; every failure is `slog.Debug` + return. Tested by `a ledger insert failure still exits 2` and `a latest-event lookup failure still exits 2` (§6.2). This is the single most important property in the change — a consolidation decision must never stop the user's work. |
| Extra query per over-threshold Stop | Low | One indexed point query (`LatestEventID`) on a path that is already doing a `SUM` over the session's unrefined events. Plan pinned by test (§6.6). |
| `requested_at` written in the wrong format | Medium | Silent, boundary-only wrongness (#1185) — hence the explicit red-before-green format test in §6.4 and the "never bind `formatTimestamp`" note in §5.2. |
| Migration number collision at merge | Low | §4.1 coordination rule; `inventoryEmbeddedMigrations` hard-errors on duplicates, so a collision fails loudly at test time, never silently. |
| Doctor Q2 unbounded on a large store | Low | Bounded by DISTINCT sessions asked in 7 days; `session_refinements` reached only by PK point lookup. Plan pinned by test (§6.6). |
| Conversion ratio misread as agent quality | Medium (human) | The hint names #2275 (reason text / skill wording) as the likely cause; the `produced_by` breakdown separates agent covers from `gc:orphan-consolidation`. |
| Golden churn hides an unrelated regression | Low | §6.7 requires a hand-diff of the regenerated golden, not a blind `-update`. |

**Rollback.** Additive table plus one additive index pair; no existing table, trigger, view or contract is touched. Nothing reads `consolidation_requests` except the new doctor check, so reverting the Go changes leaves an unread empty table — harmless. A down migration that drops it is optional; if written, it must be a separate numbered migration, never an edit to `000075` (the manifest is digest-pinned, and editing a released migration breaks every store that already applied it). A binary rolled back to before this change ignores the table entirely.

**Forward compatibility.** `signal` + the two reserved `delivery` values mean #2274 (work-based trigger) and #2275 (`additionalContext` delivery) can record honestly without a further migration. That is the point of Wave 0 landing first: everything else in the #2272 group is measured through this ledger.
