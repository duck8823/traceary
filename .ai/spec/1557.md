# #1557 MCP tool advertisement schema budget

## Structure-Behavior Design Note

### Requirement summary

- **Purpose:** Keep the existing nine-tool MCP surface fully advertised while making schema growth observable and bounded before it creates host loading or context-cost regressions.
- **Current behavior:** `TestServer_ToolRegistrySnapshot` pins names, descriptions, annotations, and input schemas, but it omits inferred output schemas and has no explicit byte budget for the runtime `tools/list` result.
- **Expected behavior:** A test-only runtime `ListTools` helper observes the actual nine-tool response. The sorted contract snapshot contains both input and output schemas; a checked-in size report records aggregate and per-tool bytes. Tests use explicit aggregate warning bands and hard limits, plus reviewed per-tool caps.
- **Compatibility invariant:** The default surface remains exactly the existing nine tools. There is no profile, lazy registration, or tool split; every host registers `traceary mcp-server` with its native manifest shape.
- **Out of scope:** Reducing schemas, changing tool names or operations, adding protocol-level pagination behavior, or asserting host-specific loading timing that the repository cannot observe without reading tool bodies.

### Conceptual model

| Concept | State | Behavior | Constraint / invariant |
| --- | --- | --- | --- |
| Runtime advertisement | `tools/list` response from an initialized in-memory server | Exposes every registered tool with inferred schemas | Exactly nine default tools; the response is the measurement source |
| Contract snapshot | Sorted, pretty JSON fixture | Pins tool metadata, input schema, and output schema | Changes require explicit `-update` review |
| Budget report | Sorted, pretty JSON fixture | Pins total, aggregate-input, and per-tool compact JSON bytes | Generated from the same runtime response as the snapshot |
| Budget policy | Hand-edited test constants | Classifies actual bytes as pass, warning band, or failure | Total `tools/list` <= 53248 B with warning from 49152 B; all input schemas <= 18432 B with warning from 16384 B |
| Host registration | Packaged MCP manifest entries | Starts the same default server command | Command is `traceary`; sole argument is `mcp-server`; host-only fields are not a tool profile |
| Loading observation | Body-free documentation matrix | Records what package manifests can prove about discovery | Values are eager, lazy, or unknown; unknown is not inferred as lazy |

### Responsibility assignment

| Responsibility | Owner | Reason to change | Not owner / reason |
| --- | --- | --- | --- |
| Build and advertise the nine tools | `presentation/mcpserver` production server | The server owns the public MCP contract | Tests do not alter runtime registration |
| Collect advertisement and calculate bytes | `presentation/mcpserver` test helper | It consumes the public `ListTools` behavior without exposing production API | Production handlers must not carry test budgeting policy |
| Enforce limits and fixture contract | MCP tests and `testdata` fixtures | CI needs deterministic drift detection | Individual tools do not self-police presentation budget |
| Keep packaged manifests on one command | `cmd/repo-tooling integrations verify` | It already owns cross-host manifest validation | Host manifests retain their native envelope formats |
| Explain observable loading state | operations documentation | Loading timing is host behavior, not a server guarantee | No body-bearing probes are introduced only to label a host eager/lazy |

### Boundaries / interfaces

| Boundary or interface | Consumer | Hidden detail | Error contract |
| --- | --- | --- | --- |
| `ListTools` over in-memory MCP transport | Contract and budget tests | Server initialization and generated schemas | Test fails when the advertised set is incomplete or bytes exceed policy |
| Compact JSON marshal of `ListToolsResult` | Budget test | JSON encoder field ordering and host transport framing | Measures protocol payload, not stdio framing |
| Sorted snapshots | Reviewers and CI | Registration order | Exact fixture diff shows schema and metadata drift |
| Integration manifest verifier | Package maintainers | JSON envelope differences and optional host cwd | Fails if a host registers a different executable/argument surface |

| Behavior | Given | When | Then | Level |
| --- | --- | --- | --- | --- |
| Complete runtime surface | Initialized default server | Client calls `ListTools` | Exactly the nine known tools are advertised once |
| Input/output contract | Runtime tool response | Snapshot is encoded and compared | Every tool's input and inferred output schema are pinned |

### Risks / rollback

- **Procedural-logic risk:** Reimplementing schema collection could measure a different shape than clients see. The helper calls `ListTools` through the SDK transport and serializes that response.
- **Premature-abstraction risk:** Tool profiles or schema loading strategies would change the public default surface without evidence they solve a current limit. This change adds only test-side observation.
- **Migration / compatibility:** No storage or runtime migration is needed. Snapshot additions are test fixtures; production tool names and operations remain unchanged.
- **Budget calibration:** The original branch measured 41,028 B for `tools/list`; `get_report` alone measured 12,370 B and also exceeded the original 90% warning threshold. After rebasing onto `origin/main` at `93b69c3a`, including merged PRs #1561 and #1566, the final runtime fixture measures 44,684 B for `tools/list` and 14,130 B for all input schemas. The revised 14 KiB `get_report` cap and 7 KiB / 8 KiB / 7.5 KiB caps for the three expanded event tools keep the final tree below warning without making the limits fixture-derived.
- **Fixture regeneration:** Both fixtures are generated in one `go test` invocation after all schema-producing branches are rebased or integrated. The final fixtures for this branch were regenerated after #1561 and #1566 reached `origin/main`; neither fixture is copied from an older parallel branch, and observed-byte updates never rewrite policy limits.
- **Rollback trigger:** If SDK serialization changes independently or a real compatible schema expansion needs more budget, review the size report and adjust the hand-edited policy in a deliberate follow-up rather than silently regenerating it.
