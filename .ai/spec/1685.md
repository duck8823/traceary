# #1685 — apply the payload codec to the existing corpus

Structure-Behavior Design Note. Risk: **High** (rewrites every body row on a 24.7 GiB live store).

Measured on 2026-08-09 against a schema-52 store built from `schema/sqlite/migrations/`, through
`modernc.org/sqlite` — the driver the product actually uses — not through the `sqlite3` shell.

> **Scope inversion.** The issue is titled "move event bodies out of the events table **and** compress
> them". The measurements below show the *move* half rests on a premise that is false, and that the
> *compress* half already has an end-to-end wiring waiting for it. This note therefore designs the
> backfill and takes the side table out of scope, with the reasoning in D1 and a follow-up issue filed.

## Requirement summary

- **Goal.** Every existing event body is stored through the versioned zstd codec that
  `infrastructure/sqlite/payload_codec.go` already implements, releasing a measured ~0.584 GiB of
  `events.body`. Bodies read identically before and after.
- **Current state.** Migration 036 shipped the whole codec contract — five metadata columns on
  `events`, compatibility counters, guard triggers — and its own header states the intent:

  > "Reader-first payload codec foundation. v0.34 writes identity only; zstd activation and **legacy
  > backfill are intentionally deferred to v0.35**."

  Not one row is compressed. **This issue is that legacy backfill.**
- **Expected behaviour.** A store part-way through the backfill is a fully valid store. `report`
  output is byte-identical. Interrupting loses nothing.
- **Not in scope.** Activating the codec for *new* writes (#1618). Deciding when to discard a body
  (#1676). Retiring `event_metadata_projection` (#1686). Compressing the three `command_audits` text
  columns (follow-up — see "Sequencing"; it is two thirds of the gate contribution and must be an
  explicit dependency of #1679 and #1620). Relocating bodies to a side table (D1).

## Facts established before designing

### The `sqlite3` shell lies about `ALTER TABLE`

An earlier draft recorded a measurement that SQLite happily drops a column referenced by a live
trigger. That measurement was invalid: **the `sqlite3` CLI sets `legacy_alter_table=ON`**, and under
it the schema is not reparsed. Under the driver (`legacy_alter_table=0`, verified by querying
`pragma_legacy_alter_table` on a driver connection):

| schema reference to `body` | `ALTER TABLE events DROP COLUMN body` |
|---|---|
| trigger *body* reads `NEW.body` | **refused**, atomically — `error in trigger t_upd after drop column: no such column: NEW.body`; column still present |
| view selects `body` | **refused** — `error in view v after drop column: no such column: body` |
| only the `AFTER UPDATE OF body` column list names it | **succeeds**, leaving `UPDATE OF body` dangling on a column that no longer exists |

The refusal is a safety net, not a hazard. The one real hazard is narrow and silent: a trigger whose
*only* reference is the `UPDATE OF` column list is not reparse-checked. Three live trigger families
are that shape (`search_projection_events_update` from 038, `literal_search_event_update` from 039,
`search_projection_complete_event_update` as recreated by 041). Recorded for whichever issue
eventually removes the column; it does not arise in this one.

### `UPDATE body=''` already returns the pages

The issue's opening premise is:

> Discarding a body becomes `UPDATE body=''`, which does not release pages [...] A side table makes
> discard a `DELETE`, returning pages to the free list for reuse. **No VACUUM.**

Measured, 50,000 rows × 4 KiB body, page_size 4096, WAL checkpointed between readings:

| | page_count | freelist | reusable |
|---|---|---|---|
| before | 56,525 | 0 | 0.0 MiB |
| after `UPDATE events SET body=''` | 56,525 | **50,000** | **195.3 MiB** of 220.8 |
| after `DELETE FROM events` | 56,525 | 56,522 | 220.8 MiB of 220.8 |

Blanking a large TEXT returns its overflow pages to the free list. It is not 0 versus 100 — it is
**88% versus 100%**. The side table's incremental space win over blanking is the ~12% of leaf space
holding the row's other columns. A body small enough to live inside its leaf page frees nothing
either way (200 B bodies × 200,000 rows: `freelist` stayed 0 across the blank).

And neither shrinks the file. `page_count` is identical in every row of that table. Returning pages
to the free list makes them *reusable*; only `store compact` returns physical bytes. "No VACUUM" in
the issue conflates the two.

### The in-place codec path is already wired end to end

| consumer | evidence |
|---|---|
| canonical audit | `infrastructure/sqlite/canonical_event_audit.go:140-161` appends the five codec columns and calls `canonicalPayload` before digesting |
| archive v1 descriptor | `domain/archive_segment.go:59` fixes all five in `archiveEventV1Columns` |
| compatibility gate | `infrastructure/sqlite/payload_codec_compatibility.go:31-40` counts non-identity rows in both `counter` and `legacy_index` mode |
| prepared-migration verifier | `infrastructure/sqlite/prepared_migration_verifier_test.go:50-55` already asserts an encoded `events.body` round-trips |

Mixed is a first-class state by construction: `payloadRow.decode` treats all-NULL metadata as legacy
plaintext, refuses *partial* metadata, and decodes `identity` and `zstd` alike. A store with 300k
rows encoded and 250k not is valid and readable at every batch boundary.

### The current write path already writes `identity`

`insertEventAndAudit` encodes as `payloadCodecIdentity` and writes all five codec columns when the
schema has them (`infrastructure/sqlite/event_delivery_store.go:176-200`). So does bundle import,
archive restore, retention restore and dedupe restore. It does **not** write `body_metadata_version`,
and it does not write `body_stored_bytes` — the 021 insert trigger fills that in.

Two consequences, both load-bearing:

- `body_metadata_version IS NULL` is **not** evidence that a row is unencoded. `body_codec` is.
- `body_codec IS NULL` is **not** a sufficient selection predicate. Everything written since v0.34
  shipped is `identity` and is exactly what this issue exists to compress.

### Event IDs are random, so the cursor cannot be `id`

`newEventID` is 16 random hex bytes (`application/usecase/id_generator.go:12-24`). Ordering by `id`
means roughly half of everything ingested during a multi-hour run lands *behind* the cursor and is
never revisited. `events.rowid` is monotonic and is the correct cursor and high-water.

### Three triggers read the body's *content*

`rg 'NEW\.body\b'` over the migrations returns exactly three files — 021, 026, 034. Everything else
names `body` only in an `UPDATE OF` column list and never inspects it.

```sql
-- 026 (supersedes 021's update trigger)
CREATE TRIGGER events_body_metadata_after_body_update AFTER UPDATE OF body ON events
FOR EACH ROW WHEN NEW.body_availability = 'available'
BEGIN UPDATE events SET body_stored_bytes = length(CAST(NEW.body AS BLOB)) WHERE id = NEW.id; END;

-- 034 update trigger, ON CONFLICT DO UPDATE arm
legacy_source_hook = CASE WHEN ... OR NEW.body IS NOT OLD.body
                     THEN excluded.legacy_source_hook            -- NEW.body LIKE '[phase:...]%'
                     ELSE event_metadata_projection.legacy_source_hook END,
body_stored_bytes  = CASE WHEN NEW.body IS NOT OLD.body AND NEW.body_availability='available'
                     THEN excluded.body_stored_bytes             -- length(CAST(NEW.body AS BLOB))
                     ELSE NEW.body_stored_bytes END,
```

Both are wrong for an encoded body, and both fail *silently*:

- `body_stored_bytes` would become the **compressed** length. It is pre-codec canonical provenance —
  `prepared_migration_verifier_test.go:50-55` says so in a comment and asserts it.
- `NEW.body LIKE '[phase:subagent]%'` cannot match a zstd BLOB, so backfilling 550k rows would reset
  every `legacy_source_hook` to NULL.

These are hazards of **encoding**, not of relocation. They land in this issue under either design.

Note also that 026's inner `UPDATE events SET body_stored_bytes=...` chain-fires 034's update trigger,
because 034 watches `body_stored_bytes` (`000034_...sql:184-201`). A single outer body UPDATE therefore
reaches the projection twice. Tests must not depend on trigger ordering.

### `payload-rehearsal` is a rehearsal, not a migration engine

An earlier draft said this issue "changes that rewrite's destination, not its protocol". Wrong in
both directions:

- It never writes a canonical column. `commitRehearsalBatch` inserts into `payload_rehearsal_rows`,
  a shadow table (`payload_rehearsal_store.go:334-362`).
- It runs on a **copy** and freezes the source outright while a run is open —
  `payload_rehearsal_freeze_events_insert` aborts *every* insert into `events`
  (`000037_add_payload_rehearsal.sql:66-83`).
- It refuses to start if the live store already holds a non-identity payload
  (`ErrLivePayloadNotIdentityOnly`, `payload_rehearsal.go:302-307, 656-661`).

Its purpose is to predict what compression would cost without touching anything. It cannot be
retargeted into a live rewrite by editing a field table.

## Conceptual model

| Concept | State | Behavior | Constraint / Invariant |
|---|---|---|---|
| Event body | plaintext (legacy) \| `identity` \| `zstd` | decodes to the same bytes in all three | codec metadata is all-NULL or all-present, never partial |
| Body provenance | `body_original_bytes`, `body_stored_bytes`, `legacy_source_hook` | reported | derived from plaintext at ingest; a change of *representation* must never disturb it |
| Body availability | `available` \| `unavailable_retention` | explains why a body is absent | orthogonal to codec — representation and presence are already separate columns |
| Backfill run | rowid high-water + rowid cursor + recipe version | advances in bounded transactions | resumable at any batch boundary; the store is valid between batches; terminates at a fixpoint |

## Decisions

### D1 — no side table in this issue

The move was justified in the issue solely on space: discard-as-DELETE returns pages, discard-as-blank
does not. That is measured false above (88% vs 100%). What remains is ~12% of a discarded body's
footprint, against this cost:

- a second table, its `ON DELETE CASCADE`, and the `ON UPDATE` question the current schema answers
  explicitly for event-ID changes (`000034_...sql:184-206`)
- a cross-table invariant SQLite's `CHECK` cannot express (no subqueries), so "is there a body"
  becomes application-enforced in every mutation path
- relocating three trigger families that key on `UPDATE OF body`
- re-wiring the four consumers listed above, each a **silent content-loss** path if missed: export
  would archive an empty body, import would create no child row, bundle replace would update only
  the parent
- `payload_codec_compatibility.go`'s `legacy_index` mode reads a partial index on `events.body_codec`;
  a side table drops out of the compatibility answer entirely

None of that buys a byte the backfill does not already buy. The codec is what shrinks the corpus.

The genuine argument for a side table is **locality**, not space: `events` is scanned for metadata far
more often than for bodies, and inline multi-KiB bodies push those scans through pages they do not
need. That is a real but unmeasured claim, it is on neither #1620 gate, and it is not what the issue
argues. Filed as a v0.34 follow-up so it can be decided on its own evidence.

### D2 — this issue adds no body-state column, and prescribes none

Representation (`body_codec`) and presence (`body_availability`) are already separate columns, so the
backfill needs no new state. This note deliberately does **not** hand #1676 a solution: extending
`body_availability`'s `CHECK` requires a table rebuild in SQLite, and `domain/types/body_availability.go:20-35`
treats anything but the literal `available` as absent. #1676 owns that model.

### D3 — `events.body` keeps its name and its column

Nothing is dropped and nothing is renamed. The column holds the encoded payload; `body_codec` says
how to read it. The `ALTER TABLE` findings above are recorded for the issue that eventually removes
the column, which cannot be this one — the column is where the payload lives.

### D4 — a new in-place backfill, resumable, on the live store

`store payload-backfill`. It walks `events` ordered by `rowid` up to a high-water fixed at run start,
and for each bounded batch, **in one transaction**:

1. re-selects the batch's rows and verifies each still hashes to what was read (a row changed under
   us is left for a later pass, never overwritten)
2. encodes each body through `payload_codec.go`
3. writes `body` and the five codec columns — and leaves `body_stored_bytes`, `body_original_bytes`,
   `source_hook` untouched
4. advances the checkpoint

**Selection predicate** — `body_codec IS NULL OR body_codec = 'identity'`, restricted to rows whose
codec metadata is all-NULL or all-present. A partially-populated row is **not** encoded and **not**
silently treated as legacy plaintext; it is counted and reported, and the run fails closed. (Migration
036 adds the five columns with no constraint tying them together, so this state is representable.)

Whether an eligible row is actually rewritten is a recipe decision, not a predicate one: a body that
does not shrink stays `identity`, with its metadata rewritten so it is no longer eligible.

**Termination** — a cursor pass alone does not finish the job. Rows skipped in step 1, and any row
the cursor has already passed, must be revisited. The run therefore repeats passes until no eligible
row remains at or below the high-water. The high-water is what makes this terminate on a live store:
without it, ingestion keeps producing eligible `identity` rows forever.

In place, on the live store, because copy-and-publish is strictly worse here:

- it needs 24.7 GiB of free space to hold the copy
- it must either freeze every writer for the whole run or re-validate the live high-water at publish
  time; the current rehearsal takes the first option and would block ingestion for hours
- and it buys nothing, because **mixed is already a valid state**. A copy exists to make an
  intermediate state invisible. Here there is no invalid intermediate state to hide.

Consequently the run needs no freeze, no publication, and no rollback exchange. A crash leaves a
valid store with a checkpoint.

Two constraints from the copy design survive:

- **The checkpoint carries a recipe version.** `payload_rehearsal_checkpoints` keys on
  `(run_id, table_kind, field_kind, last_primary_key)` alone. A run started by one binary and resumed
  by another with different batch semantics would skip a prefix it never wrote. The new checkpoint
  table records the recipe version and refuses to resume across a change.
- **The batch is atomic.** Verify-source, encode, write, checkpoint in one transaction, or a crash
  between "wrote the body" and "wrote the checkpoint" re-encodes an already-encoded row — and
  encoding a zstd BLOB a second time is not idempotent. The predicate guards this a second time.

### D5 — migration 053 makes two derivations codec-aware

Constant cost, no table rewrite, and it must land before any row is encoded — which it does, since
the migration runs at startup and the backfill is a command.

The fix is to derive from the stored bytes **only while the row is stored as plaintext**, and to carry
the value forward once it is not:

| trigger | change |
|---|---|
| `events_body_metadata_after_body_update` (026) | derive `body_stored_bytes` from `length(CAST(NEW.body AS BLOB))` only when `NEW.body_codec IS NULL OR NEW.body_codec='identity'`; otherwise keep `NEW.body_stored_bytes` |
| `event_metadata_projection_events_after_update` (034) | same guard on its `body_stored_bytes` arm; and on the `legacy_source_hook` arm, guard the `NEW.body IS NOT OLD.body` disjunct the same way, so a representation change does not re-run the `LIKE` inference |

This is deliberately the smallest change that stops the corruption. Every content-changing writer
that exists today writes `identity`, so their behaviour is bit-for-bit unchanged.

**The INSERT triggers are not touched.** This issue never inserts a row. When #1618 makes new writes
non-identity, `events_body_metadata_after_insert` (021) and 034's insert trigger will derive
`body_stored_bytes` and `legacy_source_hook` from a compressed blob, and every production writer will
have to supply plaintext provenance instead — `event_delivery_store.go:186-200` supplies neither
today. That is a precondition of #1618 and is recorded on it, not solved here.

The 038/039/041 families are genuinely untouched: they fire on `UPDATE OF body`, the backfill updates
`body`, so they fire exactly as before. See D7 for why that is the right outcome.

### D6 — SQL that *interprets* the body has to stop, or be gated

This is the largest piece of work in the issue and neither the issue nor the first draft named it.
An encoded body is a BLOB: `json_valid` returns 0, `LIKE` never matches, `length()` returns the
compressed size. Every place that asks SQLite a question *about the body's content or plaintext size*
breaks, and breaks silently — with a plausible zero or an empty match, not an error.

Swept with `rg` over `infrastructure/`, `application/`, `presentation/`, `domain/`, excluding
migrations and tests. Three categories:

**(A) Semantic interpretation — must move out of SQL.** These cannot be repaired in SQL at all.

| site | what it does |
|---|---|
| `sql/select_bounded_event_bodies.sql:12-17,47` | `json_valid` / `json_type` / `json_each(json_extract(e.body,'$.blocks'))` — derives search text from a `{blocks:[…]}` body (`event_bounded_datasource.go:19`) |
| `sql/search_event_metadata.sql:10-20` | the same derivation (`event_metadata_datasource.go:49`) |
| `sql/select_recent_events_by_source_hook_with_legacy.sql:39-41` | `e.body LIKE '[phase:subagent]%'` — the query-side twin of 034's `legacy_source_hook` inference (`event_datasource.go:32`) |

The two JSON sites are the same transformation written twice; decoding in Go and doing the extraction
there consolidates them. The `LIKE` site must consult `event_metadata_projection.legacy_source_hook`
(which D5 now preserves) instead of re-inferring from bytes it can no longer read.

**(B) Byte accounting — must say which byte it means.** `length(CAST(body AS BLOB))` silently switches
from plaintext to compressed size. The codec columns already carry both: `body_plaintext_bytes` and
`body_encoded_bytes`.

| site | which figure it wants |
|---|---|
| `sql/select_session_body_bytes.sql:3`, `sql/select_session_body_bytes_after.sql:5` | logical volume, for consolidation pressure (`domain/model/session_consolidation_pressure_repository.go:16`) → plaintext |
| `content_event_dedupe_datasource.go:284-289, 887, 933` | a size gate and dedupe statistics → plaintext for the gate |
| `payload_hydration.go:36, 139, 150` | `CASE WHEN length(CAST(body AS BLOB)) <= ? THEN body END` — a guard against materialising a huge value; the stored size is the right figure here, but the decoded size is what the caller then holds, so both bounds have to be stated |
| `search_projection_rebuild.go:375` | already asks for both, and already prefers `body_plaintext_bytes` for the logical figure — physical is intentional |

**(C) Already codec-aware, leave alone.** `literal_search_query.go:212` and
`event_search_authority.go:219` both read `COALESCE(e.body_encoded_bytes, length(e.body), 0)` and
`COALESCE(e.body_plaintext_bytes, length(e.body), 0)`, falling back to `length()` only when the
metadata is absent — which after the backfill it is not.

This cost belongs to *compression*, not to storage location: a blob is opaque to SQL wherever it
lives, so a side table would not avoid a single line of it. It is the price of the #1620 store gate.

Each site gets a test that fails against a compressed corpus before it is fixed.

### D7 — the projection is invalidated once and rebuilt, not suppressed

An earlier draft proposed suppressing projection invalidation during the run. That was wrong and it
contradicted D5. Reading the three invalidations settles it — none of them appends a row:

| trigger | effect |
|---|---|
| `search_projection_events_update` (038:11) | `revision=revision+1`, only `WHEN state='rebuilding'` |
| `search_projection_complete_event_update` (041:17-22) | sets `state='drifted'`; the `WHEN state='complete'` guard makes every later firing a no-op |
| `literal_search_event_update` (039:33-35) | `query_revision+1, state='stale'` on a singleton row |

All three are idempotent marks on singleton rows. 550k firings cost 550k trigger evaluations and
dirty one page per batch transaction; they do not grow anything. And the end state — `drifted` /
`stale` — is *correct*: the store's representation did change, and the projection should be rebuilt.

So the run suppresses nothing, changes no projection trigger, and needs no new verifier. Its
documented completion step is the existing rebuild, in the same maintenance window as `store compact`.

## Risks / rollback

- **Silent provenance corruption.** The highest risk, because it is invisible — a wrong
  `body_stored_bytes` reads as a plausible number. D5 fixes the cause; the provenance test **must be
  written to fail against today's schema before 053 is applied**. Do not accept it passing first run.
- **`legacy_source_hook` wipeout.** Same shape, 550k rows, unrecoverable without a re-derivation pass
  over plaintext that no longer exists. Same mitigation, same must-fail-first requirement.
- **Non-idempotent double encoding.** Encoding a zstd BLOB again produces a valid-looking row whose
  plaintext is a compressed blob. Guarded twice: the selection predicate and atomic batches.
- **A missed D6(A) site.** Silent: an empty search result or a NULL classification, never an error.
  This is why each site gets a test that fails against a compressed corpus first. The sweep command
  is recorded in D6 so it can be re-run after #1618, #1679 and #1686 touch the same queries.
- **Stranded rows.** A cursor over random IDs, or a conflict skip that advances the checkpoint, loses
  rows permanently and silently. The rowid cursor plus the fixpoint loop is the mitigation; the
  fixpoint test is what proves it.
- **Rollback.** There is no reverse pass, and none is needed: an encoded row decodes through a path
  that already ships in released binaries (036 landed in v0.34). The migration is additive and
  constant cost. An operator who runs the backfill and dislikes it keeps a working store.
- **Live-store rule.** `ref_live_db_migration_gap` — never point a repo build at
  `~/.config/traceary/traceary.db`. All measurement in this note used temporary databases.

## Sequencing

The issue asks to land after #1717, #1718, #1680, and before #1620 and #1676. That holds, with one
correction and one split.

**Correction.** The issue sequences #1685 before #1686. It should be the other way round, or 034's
projection has to be re-expressed here only to be deleted there. D5 keeps the re-expression to two
`CASE` guards precisely because this ordering may not change.

**Split, and its cost.** The issue's 1.67 GiB is not all `events.body`:

| source | GiB |
|---|---|
| `events.body` — prompt + transcript | **-0.584** |
| `command_audits.output_text` | -0.925 |
| `command_audits.command_text` + `input_text` | -0.162 |

Two thirds of the gate contribution is `command_audits`, which needs no trigger work and no
projection handling — three more fields through the same engine. It is split out so this PR stays
reviewable, but the split has a consequence that must be recorded on the issues, not left implicit:
