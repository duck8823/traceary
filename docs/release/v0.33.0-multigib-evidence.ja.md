# v0.33.0 multi-GiB リリース証跡

[English](./v0.33.0-multigib-evidence.md)

## 結論

**合格です。**
Go 1.26.3、darwin/arm64で実行した#1558の全証跡は、定義済みのrelease gateをすべて満たしました。
2 GiBのprojection-only直接metadata benchmarkはp95 **0.079708 ms**で、固定済みの**250 ms未満**という基準を満たしました。
copy上のmigration、event/projection件数一致、不完全/完全FTSの分離probe、MCP aggregate response budget、host verifierの事前条件、privacy、scratch cleanupも合格しました。

Phase Cのlatencyは観測値です。
#1558はPhase Cのrelease基準を定義していないため、合否には使いません。
この証跡によって#1558のblockerは解消しましたが、v0.33.0のほかのrelease gateは独立して判定します。

このbranchは、#1567と#1570を含む`main`の`6641c6d7`へrebaseしました。
projection導入前のblocked artifactにあるmetricは再利用していません。

機械可読な証跡は[`v0.33.0-multigib-evidence.json`](./v0.33.0-multigib-evidence.json)です。
metricsだけを含みます。

## 手順とprivacy境界

maintainer専用runnerは次の順で実行します。

1. scratchの空き容量が12 GiB以上であることを確認する。
2. ownerだけが読める一時directoryを作る。
3. event 8件、2 GiBのprojection-only metadata benchmarkを実行する。
4. syntheticなmigration 31適用前storeをcopyし、copyだけにmigration 31から34を適用する。
5. event/projection件数一致を確認し、130 eventのfixtureにlimit 20を指定してmetadata/boundedのlist、context、searchを各25回計測し、返却件数とmembershipの一致を検証する。
6. FTSが不完全な状態と完全な状態のsearch観測を分離する。
7. multibyte canonical blockを含む100件のMCP requestを実行し、aggregate budgetによるcontinuationを最後までたどる。
8. probe実行前に、6個のpackageで`traceary mcp-server`登録とstaged-retrieval semantic contractが一致することを確認する。
9. 最終artifactの書込み前にscratchを削除する。

child processの出力は上限付きmemory bufferだけに保持します。
artifact schemaにはevent/session identity、workspace、path、cursor、continuation、body、prompt、responseのfieldがありません。
sourceとcopyの一致は内部で検証し、digestは公開しません。

実行と検証には次のcommandを使います。

```sh
go run ./cmd/repo-tooling release run-v0.33.0-evidence \
  --output docs/release/v0.33.0-multigib-evidence.json

go run ./cmd/repo-tooling release verify-body-free-evidence \
  --input docs/release/v0.33.0-multigib-evidence.json
```

## Phase A: 直接metadata gate

| 指標 | 観測値 | 必須条件 | 結果 |
| --- | ---: | ---: | --- |
| SQLite managed bytes | 2,418,774,016 | 2 GiB以上 | pass |
| stored-body metadata bytes | 2,147,483,648 | 2 GiB以上 | pass |
| event数 | 8 | 8 | pass |
| projection row数 | 8 | event数と一致 | pass |
| missing body metadata | 0 | 0 | pass |
| projection-only ordered plan | true | true | pass |
| 返却item | 8 | 8 | pass |
| 返却body bytes | 0 | 0 | pass |
| 計測回数 | 25 | 25 | pass |
| p95 | 0.079708 ms | 250 ms未満 | **pass** |

fixtureは生成したcontent-free SQLite extentを使い、user event contentをcopyしません。
fixture作成、migration、checkpoint、容量確認、`EXPLAIN QUERY PLAN`は25回のtimerより前に実行します。
各sampleが含むのはquery実行、全rowのscan、row closeだけです。
すべての計測で8 rowを返し、iteration errorがないことも確認しました。

planは`idx_event_metadata_workspace_created_at_norm_id_desc`を使い、一時sortを作らず、authoritativeな`events` tableを参照しません。
merge済みPR #1570のtrigger-maintained projectionにより、metadata選択は2 GiBのbody extentから独立します。

#1570より前のartifactはauthoritative-table pathを計測し、正しくblockedになりました。
今回の合格値はmetricの差替えではなく、全Phaseを再実行して得た値です。

このfixtureは、8 rowが2 GiBのbody extentを持つfew-huge-rows shapeを意図的に表現します。
overflow chainからmetadataを分離できることは検証しますが、別のmany-small-rows shapeまで検証したとは主張しません。

sourceはsyntheticかつprivateです。

12 GiBのpreflightはtransient WALとtest-build fileのheadroomを別に確保します。

## Phase C: projectionとFTSの観測

各系列は25回計測です。

| 操作 | projection | FTS phase | p95 | 返却item | 返却body bytes |
| --- | --- | --- | ---: | ---: | ---: |
| list | metadata | not applicable | 1.923000 ms | 20 | 0 |
| list | bounded | not applicable | 2.827000 ms | 20 | 920 |
| list | bounded_huge | not applicable | 206.746458 ms | 1 | 500 |
| context | metadata | not applicable | 1.013833 ms | 20 | 0 |
| context | bounded | not applicable | 1.467375 ms | 20 | 920 |
| search | metadata | incomplete | 6.759792 ms | 20 | 0 |
| search | bounded | incomplete | 7.027250 ms | 20 | 920 |
| search | metadata | complete | 2.630417 ms | 20 | 0 |
| search | bounded | complete | 2.844167 ms | 20 | 920 |

8個の標準probeは130 eventのfixtureにlimit 20を指定し、20 itemを返しました。9個目の`list/bounded_huge` probeは256 MiBのsource bodyを1件選択し、明示された500 byte budget以下だけを返しました。
list、context、incomplete search、complete searchの各組でmetadata projectionとbounded projectionの内部membershipが一致しました。
FTS incomplete/complete間でもsearch membershipを維持しました。
identityはmemory内でだけ比較し、serializeしていません。
metadata projectionの返却body bytesはすべて0で、bounded projectionはすべて正のbyte数でした。
この短いsingle-host seriesはmetadata projectionとbounded projectionの性能比較を目的としていません。
p95は観測値であり、相対性能を示す根拠には使いません。

## Phase Dとhost verifierの事前条件

- 100件を要求したMCP pageは、encoded body/block bytesが65,536以下でした。
- 3 pageのobserved maximumは35 items、65,536 bytesでした。
- multibyte canonical blockを持つ100 eventがcontinuation chain全体に重複も欠落もなく1回ずつ現れました。
- requestしたevent単位の上限を超えるbodyでは`body_truncated`と元の`body_length`を確認し、ほかのcanonical eventでは`body_blocks`を確認しました。
- probe実行前に、6個のpackageでMCP registrationが一致し、byte-identicalなDiscovery → Inspection → Detailのstaged-retrieval contractにも合格しました。これはrunnerの事前条件であり、公開artifactに作為的なmetrics phaseとして記録しません。
- scratchはprivateで、artifactを書き込む前に削除済みでした。

## リリース判断

#1558のrelease gateは合格です。
残る独立したrelease checkも満たす場合、このartifactをmulti-GiB body-free evidenceとしてtagged releaseの判断に使えます。
metadata projection、migration 31から34、FTS backfill、aggregate response budget、host manifest、Go runtimeのいずれかが変わった場合は、全workflowを再実行してください。
Phase Aとcopy migrationの時間は実装とhostに依存するため、一部metricだけの再利用は認めません。

`v0.33.0`のtagged-release workflowは、GoReleaserより前にartifactをstrict modeで検証します。
artifactがmissing、blocked、malformed、またはprivacy contract違反ならpublishを停止し、operatorの記憶だけに依存しません。

### Projection rollback 証跡

Phase B は rollback 互換性も検証します。pre-projection event column shape を使う writer が移行済みの private copy に INSERT し、trigger-maintained projection がその行を記録し、transaction rollback 後に event/projection の件数が復元されることを確認します。永続 evidence には `pre_projection_writer_ok` のみを記録します。
